### 2.4 GOLDEN #4 — Cap de chunks (MAX 2 SIEMPRE)

**Input variado:** cualquier respuesta de Sofia, en cualquier flow.

**Mecanismos de defensa en v5.1:**
1. **RESPONSE FORMAT (top del prompt):** "REGLA DE LONGITUD ESTRICTA: tu respuesta DEBE ser MÁXIMO 2 chunks. NUNCA 3. NUNCA 4. NUNCA 5."
2. **DO #13:** "MAX 2 chunks (`MENSAJE 1` y `MENSAJE 2`) en el output del Structured Output Parser."
3. **DON'T #17:** "NUNCA produzcas 3 o más chunks en una respuesta."
4. **Constraint #9:** "MAX 2 chunks por turno SIEMPRE. Sin excepciones."
5. **REGLA FINAL DE LONGITUD (bottom del prompt):** "MAX 2 chunks por respuesta. SIEMPRE."
6. **Every Flow A/B/C/D/E/F** explicita "MAX 2 chunks por turno."
7. **Few-shot conv 1-7** TODOS modelan output con MAX 2 chunks. Conv 7 explícitamente compara con el bug v5 (5 chunks).

**Caso edge — Sofia genera 3 chunks por inercia:**
- El Structured Output Parser tiene schema `{MENSAJE 1, MENSAJE 2}` (verificado en JSON línea 1024 del workflow v5: `"inputSchema": "{\"output\": {\"MENSAJE 1\": \"Entiendo.\", \"MENSAJE 2\": \"Entiendo.\"}}"`).
- El Formateador es un chainLlm separado que reformatea — si Sofia produjo 3 chunks de texto, el Formateador podría chunkificarlo igual en 3.
- **Riesgo residual:** existe. Mitigación: 5 capas de regla en el prompt + few-shot.

**Mitigación adicional si el Formateador chunkifica en 3+:**
- El Formateador tiene "MAXIMO 3 LINEAS POR MENSAJE" como regla, pero NO tiene cap de chunks. Si Sofia genera output corto (2 ideas), el Formateador devuelve 2 chunks. Si Sofia genera output largo (5 ideas), el Formateador chunkifica más.
- **El fix v5.1 ataca la raíz** (Sofia genera output corto), no el síntoma (Formateador chunkificando).
- Si el bug persiste post-deploy, próxima iteración v5.2 tocará el Formateador para capar a 2 chunks duros.

**Verificación textual del prompt v5.1 (extraído del JSON):**
```
Constraint #9 presente: "MAX 2 chunks por turno SIEMPRE. Sin excepciones."
DO #13 presente: "MAX 2 chunks (MENSAJE 1 y MENSAJE 2) en el output del Structured Output Parser"
DON'T #17 presente: "NUNCA produzcas 3 o más chunks en una respuesta"
```

**GOLDEN #4: PASS** — 7 capas de regla en el prompt. Few-shot conv 7 modela el contraste con el bug v5.

## 3. Issues encontrados

### CRÍTICO (bloquea entrega)
Ninguno.

### IMPORTANTE (backlog para v5.2 si el hotfix no es suficiente)

1. **El Formateador (chainLlm) NO tiene cap declarativo de chunks.** Si Sofia genera output largo, el Formateador puede chunkificar en 3+. El fix v5.1 ataca la raíz (Sofia compactando), no el síntoma. **Si el bug 2 persiste en producción tras v5.1, el siguiente paso es modificar el prompt del Formateador para forzar MAX 2 chunks duros y/o cambiar el `inputSchema` del Structured Output Parser para rechazar más de 2 keys.**

2. **No hay forma programática de verificar que el LLM efectivamente respeta MAX 2 chunks** — solo monitoreo del output en producción. Sugerencia: agregar un Code node post-Formateador que cuente chunks y, si > 2, los concatena (con `\n\n`) a 2 max. Defensa en profundidad. **Backlog v5.2.**

### SUGERENCIA (no bloqueante)

1. El few-shot conv 7 usa el código CR-2075 exacto del caso real. Si el founder mueve esa propiedad o la borra, el few-shot sigue siendo válido como ejemplo aunque el código no exista (el LLM aprende el patrón, no el código). Aceptable.

2. La REGLA ESPECIAL "Lead pide foto explícita" lista varias frases trigger. El LLM generaliza bien a frases equivalentes a temp 0.2, pero si aparece una frase muy distinta ("una imagencita?") podría no clasificarla. Mitigación: la lista cubre los casos esperables.
