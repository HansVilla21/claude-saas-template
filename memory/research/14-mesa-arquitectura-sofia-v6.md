# Mesa Arquitectonica — Bot Sofia v6

## Contexto y trigger

El founder cuestiono la arquitectura actual del bot Sofia v6 (1 LangChain Agent con 7 tools conectadas en N8N). Su preocupacion concreta:

> "Le estamos dando demasiada responsabilidad al agente. El prompt tiene que explicar muchas cosas: como conversar + que tools usar + cuando + como + en que casos. Si falla la decision del agente, falla todo el sistema. A veces no llama las tools que deberia. Lo estamos sobrecargando mucho."

Pidio una mesa de discusion con multiples agentes evaluando escenarios. Se ejecuto via Workflow tool:

- **Phase 1 — Propuestas:** 4 arquitectos disenaron 4 arquitecturas distintas en paralelo.
- **Phase 2 — Evaluacion adversarial:** cada propuesta fue juzgada por 4 lentes independientes (reliability, cost, latency, maintenance). Total: 16 evaluaciones.
- **Phase 3 — Sintesis:** un sintetizador leyo los 4 + 16 outputs y produjo recomendacion final.

## Las 4 arquitecturas evaluadas

- **A — Status quo mejorado:** mantener 1 agente con 7 tools, iterar el prompt con few-shots + log estructurado.
- **B — Multi-agente especializado:** 2 LangChain Agents en serie (conversador sin tools + analista con tools).
- **C — Hibrido determinista:** Sofia solo conversa (sin tools). Information Extractor node convierte el turno en JSON tipado. Nodos N8N IF/Switch + HTTP escriben a Supabase via bot-actions.
- **D — Pipeline con auditor:** GPT-4 conversa sin tools y responde inmediatamente. gpt-4o-mini audita el turno y decide tools.

## Veredicto final

## Veredicto en 1 linea

Migra a C (hibrido determinista) con los 5 fixes obligatorios de reliability antes de produccion; A solo sirve como parche puente de 2 sprints mientras construis C, y B/D introducen mas complejidad que beneficio para tu escala objetivo.

## Ranking

| Arch | Score | Pro principal | Con principal | Cuando conviene |
|---|---|---|---|---|
| **C** | 7.5/10 | Determinismo en escritura a DB + JSON auditable + Sofia conversa con prompt 40% mas corto (resuelve las 5 quejas del founder de raiz) | Race condition multi-turno + extractor puede fallar silencioso + agregar tool nueva toca 4-5 lugares | Tu caso exacto: multi-tenant, escala objetivo, founder solo, robustez > velocidad de feature |
| **A** | 5/10 | Cero cambio estructural, iteracion en minutos, riesgo de romper produccion casi nulo | NO ataca la causa raiz (LLM sigue siendo SPOF); techo de calidad ~85-92% en tool-calling | Puente operativo de 2-3 sprints, NO destino final |
| **D** | 4.5/10 | Conversador sin tools + auditor pequeno separa responsabilidades manteniendo flexibilidad | Promesas rotas al lead (bot dice "te asigno con Juan" y auditor falla); Request_Handoff en gpt-4o-mini es estructuralmente debil | Solo si C demuestra ser muy rigido por casos fuera-de-schema en mes 2 |
| **B** | 3/10 | Falla parcial (lead recibe respuesta aunque analista falle) | Race condition estructural en modo paralelo + doble prompt drift + duplica superficie de mantenimiento sin proporcional beneficio | Casi nunca; los tres jueces de reliability/latency/maintenance lo marcaron como peor que C |

## Por arquitectura

### A — Status quo mejorado

- **Resumen:** Mismo workflow, prompt modular condicional + few-shots por tool + log estructurado en `bot_turns`.
- **Cost/Latency/Implementation:** 1.0-1.3x costo (claim founder) / 1.5-1.8x real sin prompt caching (cost lens). Latencia igual a hoy: 3-6s p50. Implementacion: 3-5 dias.
- **Findings adversariales criticos:**
  - **reliability HIGH (blocker):** SPOF en una sola LLM call no determinista. Sin retry/circuit-breaker/dead-letter, race conditions por mensajes paralelos del mismo lead, sin idempotencia, observabilidad sin alerting. "NO es production-ready para cientos/miles de conversaciones simultaneas."
  - **cost HIGH:** Multiplicador real 1.5-1.8x, no 1.0-1.3x. A escala (80k turnos/dia) = +$192k/mes vs status quo si seguis con GPT-4 sin prompt caching. El plan B "switchear a gpt-4o-mini" es wishful thinking sin validar con prompt mas largo.
  - **maintenance HIGH:** Few-shots embebidos en Code Node es God Object. Sin trace_id correlacionado end-to-end + tool registry como tabla Postgres + eval set blockeante en CI, "es deuda de mantenimiento desde el dia 1."
- **Veredicto:** viable como puente, descartar como destino final. NO ataca lo que el founder llama "causa raiz".

### B — Multi-agente (conversador + analista)

- **Resumen:** Dos LangChain Agents en serie. Conversador sin tools, analista con las 7 tools.
- **Cost/Latency/Implementation:** 1.3x si analista=mini / **calculo cost lens corregido: 0.66x (37% mas barato), NO mas caro** — el documento original tiene el numero invertido. Latencia: +1.5-3s real (NO paralelo verdadero en N8N). Implementacion: 2-3 dias + 3-5 dias calibracion.
- **Findings adversariales criticos:**
  - **reliability HIGH (blocker):** Race condition estructural en modo paralelo (lead manda burst de 3 mensajes en 5s, comun en WhatsApp inmobiliario → siguiente turno lee state stale). Desincronizacion semantica entre conversador GPT-4 y analista mini que no detecta lenguaje ambiguo ("ya le aviso al equipo"). Tools irreversibles (Handoff, Assign) ejecutadas por modelo barato sin gate de confianza.
  - **latency HIGH (blocker):** El "modo paralelo" NO es paralelo real en N8N — el LangChain Agent es sincrono. Latencia esperada serial: 4-8s tipicos, picos 10-15s. Cruza el umbral de 10s que el founder marco rojo.
  - **maintenance HIGH:** Doble superficie de prompts dinamicos = doble drift. Agregar tool nueva pasa de 3 pasos a tocar 5 lugares (incluyendo prompt del conversador para que NO mencione la tool). MTTR de bugs 2-3x.
- **Veredicto:** descartar. Tres lenses lo marcaron blocker y la cuarta (cost) tiene un calculo invertido que confunde el caso. C tiene mismo costo sin estos problemas.

### C — Hibrido determinista (Information Extractor + nodos N8N)

- **Resumen:** Sofia conversa sin tools (puede bajar a gpt-4o-mini). En rama paralela un Information Extractor convierte el turno en JSON tipado. IF/Switch + HTTP escriben a Supabase via el mismo bot-actions.
- **Cost/Latency/Implementation:** 0.4x (founder) / **calculo cost lens corregido: 0.019x — ~50x mas barato si todo va a mini, ~6x si Sofia queda en gpt-4o full**. Latencia hasta el reply: -1 a -3s vs status quo (mejor). Implementacion: 2-3 dias.
- **Findings adversariales criticos:**
  - **reliability HIGH (blocker, pero solucionable):** Sofia puede prometer acciones que dependen del extractor ("ya te asigne con Pedro") y el extractor falla silencioso → promesa rota. Doble LLM call serializa fail rate (~1% por turno = decenas de fallos/hora a escala). Race condition multi-turno (extractor turno N todavia escribiendo cuando llega turno N+1). Schema dinamico es SPOF multi-tenant: 1 agencia mal configurada rompe esa agencia entera sin alerta clara. Campo "confidence" del LLM no calibra bien → es teatro de seguridad.
  - **maintenance HIGH:** Agregar accion nueva toca 4-5 lugares vs 1 tool en status quo. Audit log mal especificado: necesita capturar `extractor_prompt_used + schema_version + input_crudo + modelo`, no solo el JSON output. Doble fuente de verdad (Sofia memoria conversacional + extractor turno aislado) puede divergir → "ya te dije mi nombre".
  - **cost LOW:** Es la mejor parte de la propuesta. A escala objetivo (1.2M turnos/mes) ahorra ~$15k/mes vs status quo. NO es blocker.
  - **latency MEDIUM:** Camino critico real 1.6s p50 / 3.5-4s p95 — comodamente debajo de 10s. Bottleneck real a escala es throughput de N8N self-hosted, no la arquitectura.
- **Veredicto:** **recomendado**, condicionado a cerrar los 5 fixes de reliability antes de produccion (ver siguiente seccion).

### D — Pipeline secuencial con auditor

- **Resumen:** GPT-4 conversa sin tools y responde inmediatamente. gpt-4o-mini audita el turno y devuelve JSON con tools a ejecutar.
- **Cost/Latency/Implementation:** 1.03x (founder) / **calculo cost lens corregido: 0.66x — 33% mas barato, no igual**. Latencia percibida igual a hoy (send antes del auditor) pero acciones se aplican 1-2s tarde. Implementacion: 2-3 dias + 1 semana calibracion.
- **Findings adversariales criticos:**
  - **reliability HIGH (blocker):** Send WhatsApp ANTES del auditor crea estado inconsistente irrecuperable cuando el auditor falla — promesa rota al lead permanente. Request_Handoff (la tool MAS critica del negocio) corre en gpt-4o-mini que es estructuralmente debil para detectar frustracion sutil ("este bot no me convence", sarcasmo, frustracion acumulada). Sin idempotencia → retries duplican Tags/Notes/Assigns. Split Out + 7 HTTP paralelos sin orden semantico (Qualify se ejecuta antes que Extractor termine = califica sobre state viejo). YCloud webhook sin dedup → bot responde dos veces.
  - **maintenance HIGH:** Doble fuente de verdad para "cuando llamar tool" (conversador implicito + auditor explicito) requiere mantener 2 prompts en sync. Agregar tool nueva = 4-5 archivos vs 1. El "fallback rule-based" propuesto crece sin techo hasta convertir el sistema en Frankenstein. Bug clase "auto_actions.qualify=false en agency X pero el auditor lo llama igual" es silencioso multi-tenant.
- **Veredicto:** descartar para tu escala. C entrega el mismo valor (separar conversar de actuar) sin pagar el costo de coordinar dos LLMs.

## Riesgos a vigilar para la elegida (C)

1. **Promesas rotas al lead:** prohibir a Sofia prometer acciones especificas en lenguaje imperativo ("te asigno con Pedro"). Debe hablar en condicional ("voy a registrar eso para que un agente te contacte"). Esto se calibra en el prompt del conversador y se valida con eval set.
2. **Race condition multi-turno:** advisory lock en Postgres por `lead_id` durante el turno, o re-leer `lead.attributes_actuales` DENTRO del Code node del schema dinamico (paso 7), no usar el snapshot del paso 3.
3. **Schema dinamico SPOF multi-tenant:** tests unitarios obligatorios con fixtures de 5+ `agency.settings` reales antes de cada deploy. Tratarlo como migracion de DB.
4. **Hallucinations del extractor sin validacion deterministica:** reemplazar el campo `confidence` del LLM por regex/parsing del mensaje literal para budget/email/phone, y match estricto contra enums agency-scoped para stage/tags. El confidence del LLM es teatro.
5. **Cobertura del schema vs casos fuera-de-schema:** mantener UNA tool en Sofia como escape hatch (`request_clarification` o equivalente) para no perder capacidad conversacional rica cuando aparece algo que el extractor no captura.

## Plan de migracion (recomendacion = C, NO es A)

**Total: ~12-15 jornadas-dev en 3-4 semanas calendario. Encaja en el mes que tenes hasta produccion real.**

**Semana 1 — Foundation (4-5 jornadas)**

1. Capturar golden set de 50-100 conversaciones reales de Sofia v6 etiquetadas con tools esperadas (1-2 jornadas). Sin esto, todo lo demas es a ciegas.
2. Crear harness de evaluacion N8N (workflow separado) que corre el golden set contra cualquier arquitectura y mide tool-call accuracy + latencia + costo (1 jornada).
3. Implementar prompt caching en el Code Node del prompt actual de Sofia (estatico arriba, dinamico abajo) — beneficia A si queda como puente y baja costo en cualquier escenario (0.5 jornadas).
4. Definir schema de `audit_log` con todo el contexto reproducible: `extractor_prompt_used`, `schema_version_hash`, `input_crudo`, `modelo`, `tokens_in/out`, `latencia_por_nodo`, `trace_id` correlacionado end-to-end (1 jornada).
5. Implementar idempotencia en bot-actions edge function via `turn_id + tool + params_hash` como unique key (1 jornada). Tambien sirve para A.

**Semana 2 — Build C (4-5 jornadas)**

6. Construir workflow C en paralelo al actual (Sofia v6 sigue en produccion): quitar tools del Agent, simplificar prompt, agregar rama paralela con schema dinamico + Information Extractor + 6 IF/Switch + HTTP Requests (2-3 jornadas).
7. Validacion deterministica post-extractor (regex sobre mensaje literal para budget/email/phone, enum match estricto para stage/tags) (1 jornada).
8. Advisory lock por `lead_id` en bot-actions edge function para evitar race conditions multi-turno (0.5 jornadas).
9. Retry exponencial + DLQ procesable (`bot_action_dead_letter` con worker cada 5min) en los HTTP Requests (1 jornada).

**Semana 3 — Calibracion (3-4 jornadas)**

10. Correr harness de evaluacion contra C con golden set. Comparar A vs C en accuracy/latencia/costo (1 jornada).
11. A/B test calidad conversacional Sofia gpt-4o-mini vs gpt-4o full con 50 conversaciones reales (1-2 jornadas). Si mini es suficiente, ahorro real ~50x; si no, gpt-4o sigue siendo 6x mas barato que GPT-4.
12. Calibrar prompts (conversador + extractor) con learnings del golden set (1 jornada).
13. Capturar skill `agregar-accion-al-hibrido-determinista` con checklist de los 4-5 archivos que cambian (0.5 jornadas). NO posponer.

**Semana 4 — Hardening + cutover**

14. Dashboard de tasa-de-extractor-fail por agencia con alerta si pasa 2% (0.5 jornadas).
15. Canary cutover: 10% trafico a C → 50% → 100% en 1 semana, con rollback button al workflow viejo (1 jornada).

## Que NO se debe hacer

- **No mezcles A y C en el mismo workflow.** Si A queda como puente operativo mientras construis C, deben ser dos workflows N8N separados con switch por `agency_id` (o feature flag), nunca el mismo Agent decidiendo a veces y un extractor decidiendo otras veces. Duplica debugging.
- **No bajes Sofia a gpt-4o-mini sin A/B test con golden set.** El ahorro de 30-50x es real solo si la calidad conversacional aguanta. Para inmobiliaria (donde el tono y empatia importan en la captacion), mini puede sentirse robotico. Si no aguanta, gpt-4o full sigue siendo 6x mas barato — usarlo y seguir.
- **No confies en el campo `confidence` del LLM como gate de seguridad.** gpt-4o-mini no calibra bien su confidence; pedirle a un LLM que se autoevalue es notoriamente poco confiable. Usar validacion deterministica (regex + enums).
- **No ejecutes las acciones del extractor en paralelo sin orden semantico.** Extractor → Qualify → Stage → Tag → Assign → Note → Handoff. Performance no es el cuello de botella aca; consistencia si.
- **No dejes que Sofia prometa acciones imperativas.** "Te asigno con Pedro" → "voy a registrar tu interes para que un agente te contacte". El conversador no sabe si el extractor va a ejecutar — debe hablar en condicional.
- **No mergees C sin idempotencia en bot-actions.** Retries de N8N + 503 ocasionales de Supabase Edge garantizan que sin idempotencia vas a duplicar Tags/Stages/Handoffs en produccion el primer mes.
- **No avances a 100% sin canary.** Cutover gradual con boton de rollback al workflow A mejorado. Si la tasa de extractor-fail sube >2% en alguna agencia, rollback automatico.
- **No descartes A como puente si C se atrasa.** Si en semana 3 la calibracion de C no pasa el eval (<90% tool-call accuracy), tenes A mejorado funcionando en produccion como fallback. NO ir a produccion con C sin pasar el eval — el costo de un bot que rompe deals es mayor que el costo de seguir con A 2 semanas mas.

# Apendice A — Las 4 propuestas en detalle

Cada arquitectura fue propuesta por un agente independiente con el mismo brief y contexto. Los numeros (costo, latencia) son estimaciones del proponente; las correcciones del juez de cost lens estan en el Apendice B.

## Status quo mejorado (1 agente, 7 tools)

**Key:** `A-status-quo`

**Resumen:** Iterar el sistema actual sin cambiar arquitectura: mismo workflow N8N, mismas 7 tools, mismo bot-actions edge function. La mejora es 100% en el Code Node 'Componer System Prompt' (modular, condicional por auto_actions, con few-shots curados por tool y anti-patterns) mas un nodo nuevo de logging estructurado para iterar con data en vez de a ciegas. Bajo costo, bajo riesgo, alta velocidad de iteracion — pero no resuelve la queja de fondo del founder ('demasiada responsabilidad al agente'); la mitiga.

### Flujo propuesto

FLUJO N8N (sin cambios estructurales vs status quo, solo se reescribe el bloque 'Componer System Prompt' y se reordenan reglas):\n\n1) Trigger YCloud Webhook (POST entrante WhatsApp) -> normaliza payload (wa_id, phone, mensaje, agency_phone_id).\n2) Resolve Agency (Postgres node) -> SELECT agencies.id, settings, bot_config, auto_actions, pipeline_stages, lead_attributes_schema WHERE inbound_phone_id = $json.agency_phone_id.\n3) Resolve / Upsert Lead (Postgres) -> busca lead por phone+agency_id, crea si no existe, devuelve lead.id, stage_actual, attributes, handler.\n4) Gate Handler (IF node) -> si handler='human', salta al nodo 'Log Skipped' (no invoca LLM, solo persiste mensaje). Si handler='bot', continua.\n5) Load Conversation History (Postgres) -> ultimas N mensajes para warm-up de memoria (la memoria del Agent node de N8N tambien lee Postgres pero este SELECT extra sirve para meter resumen breve en el prompt si la conversacion es larga).\n6) Componer System Prompt (Code Node — JS) -> ESTE es el nodo donde se concentra la mejora. Construye el prompt en bloques ordenados:\n   - Bloque 1 ## QUIEN SOS (estatico por agency).\n   - Bloque 2 ## CONTEXTO DEL LEAD (dinamico: stage_actual, attributes ya capturados, ultimos 3 mensajes).\n   - Bloque 3 ## TONO (de bot_config).\n   - Bloque 4 ## AUTO-ACCIONES PERMITIDAS (de auto_actions: lista solo las tools habilitadas para esta agency — si auto_actions.assign=false, ni se menciona Assign_Tool en el prompt; reduce ruido).\n   - Bloque 5 ## CUANDO USAR CADA TOOL (NUEVO, calibrado): para cada tool habilitada, un mini-bloque con (a) trigger semantico claro ('si el lead te dice su presupuesto, llama Extractor_Tool con attributes.budget=...'), (b) 2 few-shots concretos por tool (input lead -> tool_call esperado), (c) anti-pattern ('NO uses Stage_Tool si el lead solo saludo').\n   - Bloque 6 ## ETAPAS DEL PIPELINE (de pipeline_stages, con criterio de avance entre cada una).\n   - Bloque 7 ## DATOS A CAPTURAR (schema de lead_attributes_schema).\n   - Bloque 8 ## REGLAS DURAS (top 5, no mas): no inventar precios, no prometer visitas sin Assign, pedir handoff si lead pide humano explicito, etc.\n   - Bloque 9 ## FORMATO DE RESPUESTA (corto, WhatsApp-style, max 3 lineas).\n   El Code Node devuelve { systemPrompt, agencyContext } y mete length check (warn si > 4500 tokens).\n7) Sofia Agent (LangChain Agent node, GPT-4 o gpt-4o configurable) con:\n   - Chat Model: OpenAI Chat Model node (mismo que hoy).\n   - Memory: Postgres Chat Memory (mismo schema actual, key = lead.id).\n   - System prompt: el armado en (6).\n   - User message: ultimo mensaje del lead.\n   - 7 Tools conectadas (mismas que hoy, sin cambios en su definicion ni en bot-actions): Extractor_Tool, Stage_Tool, Qualify_Tool, Assign_Tool, Tag_Tool, Note_Tool, Request_Handoff_Tool.\n8) Log LLM Decision (Code Node) -> persiste en tabla bot_turns: lead_id, system_prompt_hash, tools_invocadas[], tools_no_invocadas_evaluables[], tokens_in, tokens_out, latency_ms. Sirve para debugging y para iterar el prompt con data.\n9) Send WhatsApp (HTTP Request a YCloud) -> envia la respuesta texto del agente al lead.\n10) Realtime Broadcast (Supabase realtime.send) -> notifica al Inbox del CRM que hay mensaje nuevo + tools ejecutadas.\n\nDIFERENCIAS CONCRETAS vs status quo:\n- Prompt pasa a ser modular y CONDICIONAL (solo incluye tools habilitadas via auto_actions -> menos tokens irrelevantes).\n- Few-shots POR TOOL agregados en Bloque 5 (lo que mas mueve la aguja segun la queja del founder de 'no llama las tools que deberia').\n- Nodo 8 (Log LLM Decision) es nuevo y critico: sin esto, iterar el prompt es a ciegas. Captura tokens y latencia para optimizar.\n- Anti-patterns explicitos por tool (no solo 'cuando usarla' sino 'cuando NO').

### Pros

- Cero cambios estructurales en N8N ni en bot-actions: el riesgo de romper algo que ya funciona en produccion es minimo. Compatible con la fase de pruebas actual y con el milestone Inbox live ya cerrado (2026-05-18).
- Iteracion ultra-rapida: editar el Code Node 'Componer System Prompt' y redeploy es minutos, no dias. Permite calibrar muy rapido durante el mes previo a produccion real.
- El prompt condicional por auto_actions ya reduce tokens irrelevantes (si la agency no tiene Assign habilitada, no mete instrucciones de Assign). Ahorro real, no marketing.
- Few-shots por tool atacan DIRECTAMENTE la queja del founder ('no llama las tools que deberia'). Es el patch con mejor ROI sin tocar arquitectura.
- Nodo 'Log LLM Decision' + tabla bot_turns convierte iteracion a ciegas en iteracion con data. Inversion chica, payoff alto para todo lo que venga despues (incluido migrar a B/C/D si esto no alcanza).
- Mantiene la decision en el LLM, que es lo que mejor maneja casos ambiguos del mundo real conversacional (saludo, smalltalk, preguntas off-topic). No fuerza determinismo donde no lo necesitas.

### Cons

- Prompt sigue creciendo: cada tool nueva o regla nueva = mas tokens, mas costo por turno y mas riesgo de que el LLM 'pierda' instrucciones lejanas (lost-in-the-middle).
- Riesgo de regresion al iterar: tocar el prompt para corregir un caso (ej. mejorar Extractor) puede degradar otro (ej. Stage deja de moverse). Sin tests automatizados es ruleta.
- Decision de tool sigue siendo 100% del LLM: si el modelo no llama la tool, no hay safety net. El founder ya reporto este sintoma; el prompt mas largo no garantiza solucionarlo.
- Few-shots inflan tokens rapido: 7 tools x 2 ejemplos cada una x ~150 tokens = ~2.1k tokens extra solo en ejemplos, sumados al prompt dinamico actual (~3k). Acercandose al limite practico de atencion efectiva.
- Difusion de responsabilidad: el mismo LLM debe conversar (tono, ventas, SPSP), extraer (datos del lead), decidir (cuando calificar/handoff) y elegir tools. Mantener las 4 tareas calibradas en un solo prompt escala mal con mas verticals (no solo inmobiliaria).
- Debugging dificil: cuando algo falla, solo tenes 'el LLM decidio mal'. Sin logs estructurados de la decision (qual tool considero, por que no la llamo), iterar es a ciegas.

### Riesgos

- Riesgo principal: el founder ya identifico que 'le estamos dando demasiada responsabilidad al agente'. Esta opcion NO ataca la causa raiz — la mitiga via mejor prompt, pero el LLM sigue siendo SPOF. Si en 2-3 sprints sigue fallando llamadas de tool, hay que migrar a C (hibrido determinista) o D (pipeline con auditor).
- Riesgo de techo de calidad: con 7 tools, even un prompt perfecto da ~85-92% de accuracy en decisions complejas. Para escalar a cientos/miles de conversaciones simultaneas con muchas agencies, ese 8-15% de error se convierte en muchos leads quemados. Hay que medir con bot_turns desde el dia 1.
- Riesgo de prompt drift: cada agency tiene bot_config distinto + cada vertical futuro (no solo inmobiliaria) suma reglas. Sin tests automatizados (golden set de conversaciones esperadas), iterar el prompt rompe casos viejos sin avisar. Mitigacion: armar un eval set de 30-50 conversaciones marcadas con tools esperadas y correrlo antes de cada cambio.
- Riesgo de costo si se queda en GPT-4: con prompt mas largo + scale, el costo por conversacion sube. Plan B obligatorio: validar gpt-4o-mini con el mismo eval set; si pasa con >90% de accuracy, switchear y ahorrar 30x.
- Riesgo de latencia con tools en paralelo: si el LLM decide invocar 3 tools en un turno, el Agent node N8N las ejecuta y suma latencia (cada call a bot-actions ~200-400ms). Con GPT-4 puede irse a 8-10s percibidos. Mitigacion: monitorear latency_ms en bot_turns y poner cap (ej. max 2 tools por turno via prompt rule).

### Implementacion

- **Nivel:** baja
- **Razon:** No hay cambios estructurales en el workflow N8N (mismos nodos, mismas tools, mismo bot-actions edge function). El trabajo es: (1) reescribir el Code Node 'Componer System Prompt' con bloques modulares y condicional por auto_actions (~1 dia), (2) escribir few-shots curados por tool con ejemplos reales del dominio inmobiliario (~1-2 dias, hay que recolectarlos de conversaciones reales), (3) agregar nodo 'Log LLM Decision' + tabla bot_turns en Supabase (~0.5 dia), (4) evaluar manualmente con 20-30 conversaciones sinteticas antes de mergear (~1 dia). Total: 3-5 dias. Sin nueva infra, sin cambios de schema mayores, rollback es revertir el Code Node.

### Costo y latencia (proponente)

- **Costo vs status quo:** 1.0x-1.3x (input prompt crece ~30-50% por few-shots; output similar). Con GPT-4: ~$0.04-$0.05 por turno. Con gpt-4o-mini: ~$0.0013-$0.0017 por turno.
- **Latencia vs status quo:** +0ms a +200ms. El prompt mas largo agrega ~50-150ms de procesamiento del lado de OpenAI (tokens input mas grandes). Si se mantiene GPT-4: total 3-6s por turno (igual que hoy). Si en paralelo se baja a gpt-4o: total 1-2s (mejora neta, no atribuible a esta arquitectura sino al modelo).

## Multi-agente especializado (conversador + analista)

**Key:** `B-multi-agente`

**Resumen:** Dos agentes LangChain en serie dentro del mismo workflow N8N. El conversador (GPT-4) solo decide QUE responder al lead, sin tools; el analista (gpt-4o-mini con las 7 tools de bot-actions) recibe el turno completo (mensaje del lead + reply del bot + memoria reciente) y decide QUE acciones de DB ejecutar. Separa "estilo conversacional" de "logica de CRM", reduce el tamano de cada prompt ~40%, pero duplica las LLM calls y agrega latencia salvo que se envie el reply al lead antes de esperar al analista.

### Flujo propuesto

FLUJO N8N NODO-POR-NODO:

1) **Trigger YCloud Webhook** (POST /webhook/ycloud-inbound) — recibe mensaje del lead.

2) **Resolve Agency** (Supabase node SELECT agencies WHERE phone_number_id=...) — devuelve agency_id + settings + bot_config + auto_actions.

3) **Upsert Conversation + Insert Message inbound** (Supabase nodes) — persiste el inbound antes de hacer cualquier cosa.

4) **Componer System Prompt CONVERSADOR** (Code node JS) — arma prompt SOLO con bloques:
   - ## QUIEN SOS (nombre del bot, agencia)
   - ## TU TRABAJO (conversar con leads, calificar implicitamente)
   - ## SOBRE ESTE NEGOCIO (zona, propiedades, diferenciadores)
   - ## TONO (formal/casual segun agency.bot_config.tone)
   - ## ETAPAS DEL PIPELINE (solo lectura, para contexto)
   - ## DATOS A CAPTURAR (que info pedir, en que orden)
   - ## REGLAS DE CONVERSACION (no inventar, handoff si X)
   - NO incluye: descripcion de tools, cuando llamarlas, gates de auto_actions.
   Output: prompt ~1500-1800 tokens (vs ~3000 del status quo).

5) **Agente CONVERSADOR — LangChain Agent node** (GPT-4 o GPT-4 Turbo):
   - Chat Model: OpenAI gpt-4-turbo
   - Memory: Postgres Chat Memory (mismo session_key=conversation_id que hoy)
   - Tools: NINGUNA
   - System prompt: el del paso 4
   - User input: mensaje del lead (raw)
   - Output: string con el reply.

6) **Send WhatsApp Reply via YCloud** (HTTP Request a YCloud API) — DISPARA INMEDIATAMENTE el reply al lead. Esto es clave para no acumular latencia: el lead recibe respuesta mientras el analista corre en paralelo. (Si el founder prefiere serial estricto por seguridad, mover este nodo despues del paso 9.)

7) **Insert Message outbound** (Supabase) — persiste el reply del bot en messages.

8) **Componer System Prompt ANALISTA** (Code node JS) — arma prompt SOLO con:
   - ## ROL (sos un analista silencioso, NO conversas, decidis acciones)
   - ## INPUT que vas a recibir (ultimo turno: lead_msg + bot_reply + ultimos 6 turnos de memoria + estado actual del lead: stage, attributes, qualified)
   - ## TOOLS DISPONIBLES (7 tools con cuando invocar cada una, ejemplos few-shot)
   - ## AUTO-ACCIONES PERMITIDAS (gates de agency.auto_actions.* — si esta en false, no llamar esa tool)
   - ## ETAPAS DEL PIPELINE (con criterios de transicion)
   - ## DATOS A CAPTURAR (mapeo dato extraido -> tool a invocar)
   - ## REGLA DURA: si no hay senial clara de accion, NO invoques nada. Mejor no actuar que actuar mal.
   Output: prompt ~1200-1500 tokens.

9) **Agente ANALISTA — LangChain Agent node** (gpt-4o-mini recomendado, GPT-4 si el founder quiere conservar precision):
   - Chat Model: OpenAI gpt-4o-mini
   - Memory: NINGUNA (es stateless por turno — el contexto viene en el user input)
   - Tools: las 7 actuales (Extractor, Stage, Qualify, Assign, Tag, Note, Request_Handoff) — apuntando al mismo bot-actions edge function
   - System prompt: el del paso 8
   - User input (JSON serializado en string): {lead_msg, bot_reply, last_6_turns, lead_state:{stage, attributes, qualified, assigned_to}}
   - Output: el agente puede invocar 0..N tools, devuelve un resumen textual (que se ignora — solo importan los side effects de las tools).

10) **Log Analyst Decisions** (Supabase Insert en tabla bot_decisions_log) — guarda: turn_id, tools_invoked[], analyst_reasoning, latency_ms. Esto es CRITICO para auditar fallos del analista y calibrar el prompt sin ciegos.

11) **End** — workflow termina.

VARIANTE SERIAL ESTRICTO (mas robusta, mas lenta): mover el nodo 6 (Send WhatsApp) despues del 10. Esto garantiza que si el analista cambia el stage o pide handoff, el reply al lead refleja ese cambio. Tradeoff: +1-2s de latencia percibida por el lead.

DATOS QUE PASAN ENTRE NODOS:
- Webhook -> Resolve Agency: phone_number_id, lead phone, message text
- Resolve Agency -> Componer Prompt Conversador: agency_id, settings, bot_config
- Componer Prompt -> Agente Conversador: system_prompt (string), user_input (lead msg)
- Agente Conversador -> Send WhatsApp: bot_reply (string)
- Send WhatsApp + Insert Outbound -> Componer Prompt Analista: lead_msg + bot_reply + ultimos turnos + lead_state (consulta a Supabase)
- Componer Prompt Analista -> Agente Analista: system_prompt + JSON con turno + estado
- Agente Analista -> bot-actions edge function (via tools): mismas calls que hoy

### Pros

- Separa concerns reales: el conversador solo aprende a hablar, el analista solo aprende a decidir acciones. Cada prompt es ~40% mas corto y se puede iterar/calibrar por separado sin romper el otro lado.
- Permite usar modelos diferentes: GPT-4 para el conversador (donde la calidad de lenguaje importa), gpt-4o-mini para el analista (donde solo importa decidir tool calls bien estructurados). Costo total puede quedar cerca del status quo.
- Si el analista falla (no llama tool que deberia), el lead igual recibio una respuesta razonable del conversador. Falla parcial en vez de falla total — exactamente lo que pide el founder.
- El analista al ver el TURNO COMPLETO (lead + reply del bot) tiene mas senial para decidir tool calls que el agente unico que decide ambas cosas en una sola pasada. Empiricamente menos 'olvidos' de tool calls.
- Audit trail nativo: la tabla bot_decisions_log te da metricas exactas de cuando el analista llamo / no llamo tools, sin parsear traces de LangChain. Calibrar prompts se vuelve data-driven.
- Si en V2 quieres reemplazar el analista por algo determinista (Information Extractor + nodos condicionales, opcion C), el conversador queda intacto y la migracion es incremental.

### Cons

- 2x LLM calls por turno = costo aumenta. Mitigado si analista=gpt-4o-mini (~1.3x total), pero si analista queda en GPT-4 es ~2x. A escala de miles de conversaciones, importa.
- Latencia end-to-end aumenta. En modo paralelo (reply al lead antes de esperar analista) el lead no lo siente, pero la DB queda inconsistente por 1-2s — el lead podria mandar otro mensaje antes de que se aplique el stage change. Race condition.
- El analista NO ve la respuesta que el conversador va a dar antes de que la decida, pero SI la ve despues. Si el conversador prometio algo ('te paso con un humano'), el analista tiene que detectarlo y llamar Request_Handoff. Si el prompt del analista no esta bien calibrado para leer la respuesta del bot, se desincronizan los dos.
- Mas piezas moviles = mas que mantener. Dos prompts dinamicos en vez de uno; dos sets de logs; dos puntos de fallo (timeout, rate limit, parser error en cada agente).
- El conversador no tiene contexto del estado de la DB despues del turno (no sabe si se hizo Stage_Tool). Si el lead pregunta '¿ya me asignaste a alguien?', el conversador no puede responder con certeza salvo que reciba el estado actualizado en el siguiente turno via memoria/contexto.
- Para extraer datos sensibles del lead (nombre, email, presupuesto) el analista corre DESPUES del reply. Si el conversador no recolecto los datos en su turno (porque no es su trabajo activo), el ciclo de captura puede sentirse mas lento — necesita 2-3 turnos para capturar lo que hoy se captura en 1.

### Riesgos

- Desincronizacion conversador-analista: el conversador dice 'te paso al equipo humano' pero el analista no detecta la senial y no llama Request_Handoff. Mitigacion: prompt del analista con few-shots explicitos de 'si bot_reply contiene X, llama tool Y' + test suite de turnos sinteticos.
- Race condition en modo paralelo: lead manda mensaje 2 antes de que el analista del turno 1 termine de escribir en DB. El conversador del turno 2 lee estado stale. Mitigacion: usar serial estricto (mas lento pero consistente) o lockear conversation_id con SELECT FOR UPDATE en bot-actions.
- Costo descontrolado a escala: si una agencia tiene 1000 leads/dia activos = 2000 LLM calls/dia solo por turnos del bot. Mitigacion: gpt-4o-mini para analista + cache de system prompts via OpenAI prompt caching (ahorra ~50% en el prompt repetido).
- Debugging cruzado mas dificil: cuando algo sale mal, hay que mirar dos traces de LangChain Agent y correlacionarlos por conversation_id. Mitigacion: log de bot_decisions_log con request_id compartido + dashboard en CRM admin para inspeccionar turnos.
- Lock-in al patron multi-agente: una vez que el founder se acostumbra a iterar dos prompts, volver a un solo agente (status quo mejorado) se siente como retroceso aunque sea lo correcto. Mitigacion: dar 2 semanas de prueba con metricas claras (tool-call accuracy, latencia, costo) antes de declarar la arquitectura final.
- Tools con efectos secundarios irreversibles (Request_Handoff alerta Telegram, Assign notifica al user) ejecutadas por analista mini pueden disparar falsos positivos. Mitigacion: para tools criticas (Handoff, Assign) requerir un score de confianza minimo o un segundo paso de validacion deterministica antes de ejecutar.

### Implementacion

- **Nivel:** media
- **Razon:** El workflow N8N actual ya tiene la mitad de la infraestructura: tools conectadas a bot-actions, memoria Postgres, composer dinamico de prompt. Lo nuevo: (1) duplicar el nodo de composer (uno para conversador sin tools-info, otro para analista con tools-info), (2) agregar segundo LangChain Agent node con las 7 tools movidas, (3) decidir paralelo vs serial estricto para el Send WhatsApp, (4) tabla bot_decisions_log + nodo de insert, (5) reescribir ambos prompts (mas chico cada uno pero hay que hacerlo bien y testear). Estimado: 2-3 dias de desarrollo + 3-5 dias de calibracion de prompts con conversaciones reales antes de produccion. La parte dificil no es N8N — es escribir el prompt del analista de manera que detecte seniales de tool-call sin sobreactuar (false positives en Handoff/Assign son caros).

### Costo y latencia (proponente)

- **Costo vs status quo:** ~1.3x si analista=gpt-4o-mini (recomendado); ~2x si analista=GPT-4. Status quo (GPT-4 + 7 tools) ~$0.04/turno; arquitectura B con conversador GPT-4 + analista mini ~$0.05/turno
- **Latencia vs status quo:** +1.5s a +3s end-to-end. Status quo 3-6s; arquitectura B: conversador 2-4s (responde al lead inmediatamente despues) + analista 1-2s en paralelo si el reply al lead se manda antes de esperar al analista. Si se hace estrictamente serial: +2.5s tipico

## Hibrido determinista (Information Extractor + nodos N8N)

**Key:** `C-hibrido-determinista`

**Resumen:** Hibrido determinista separa "conversar" de "actuar": Sofia (LangChain Agent SIN tools, ideal gpt-4o-mini) responde al lead, y en paralelo un Information Extractor convierte el turno en JSON tipado que nodos IF/Switch + HTTP Request escriben a Supabase via el mismo edge function bot-actions. Resuelve directamente las 5 preocupaciones del founder — agente con menos carga cognitiva, prompt mas corto, escritura a DB 100% determinista y auditable — a cambio de menos flexibilidad ante casos no contemplados en el schema y un segundo LLM call por turno.

### Flujo propuesto

FLUJO N8N PASO A PASO (arquitectura C - Hibrido determinista):

1) TRIGGER YCLOUD WEBHOOK — recibe mensaje entrante de WhatsApp. Output: { wa_id, phone, text, conversation_id, agency_phone_number_id }.

2) RESOLVE AGENCY (Postgres node) — query por agency_phone_number_id -> devuelve { agency_id, agency_name, agency.settings, agency.bot_config, agency.auto_actions }. Misma logica que hoy.

3) RESOLVE LEAD + CONVERSATION (Postgres node) — busca/crea lead por phone+agency_id, busca/crea conversation. Output: { lead_id, conversation_id, lead.attributes_actuales, lead.current_stage, lead.qualified, lead.tags }.

4) COMPONER SYSTEM PROMPT (Code node) — arma prompt SIMPLIFICADO comparado al status quo: solo bloques de ## QUIEN SOS, ## TU TRABAJO (conversar y descubrir), ## SOBRE ESTE NEGOCIO, ## TONO, ## ETAPA ACTUAL DEL LEAD, ## DATOS YA CAPTURADOS, ## REGLAS DE CONVERSACION. SE QUITAN los bloques ## AUTO-ACCIONES PERMITIDAS y ## CUANDO USAR CADA TOOL — el agente ya no decide acciones. Reduccion estimada: de ~3000 a ~1800 tokens input.

5) SOFIA CONVERSA (LangChain Agent node, SIN TOOLS) — solo Chat Model (gpt-4o-mini recomendado, ya no decide acciones) + Postgres Memory. Input: system prompt + ultimo mensaje del lead. Output: { assistant_reply } texto puro. Aqui esta el ahorro: sin tools el modelo chico es competente para conversar.

6) ENVIAR REPLY A WHATSAPP (HTTP Request a YCloud) — manda assistant_reply al lead INMEDIATAMENTE. El lead recibe respuesta en ~2s. NO esperamos al extractor — se ejecuta en paralelo (siguiente rama).

7) RAMA PARALELA desde el output de paso 3 (Resolve Lead): COMPONER SCHEMA DINAMICO (Code node) — lee agency.settings.pipeline_stages, agency.settings.allowed_tags, agency.bot_config.datos_a_capturar y construye dinamicamente el JSON schema del extractor: { name?: string, phone?: string, email?: string, budget?: number, zone?: string, stage_change?: enum<stages_de_esta_agencia>, qualified?: boolean, qualified_reason?: string, tags?: array<enum<tags_permitidos>>, handoff_reason?: string, note?: string }. Todos opcionales — el extractor solo llena lo que detecta.

8) INFORMATION EXTRACTOR (LangChain Information Extractor node con gpt-4o-mini) — input: ultimo mensaje del lead + assistant_reply de Sofia + lead.attributes_actuales (para contexto "que ya sabemos"). Prompt del extractor: "Analiza el turno y extrae SOLO lo que el lead dijo o confirmo explicitamente en este mensaje. NO inventes. NO repitas datos ya capturados (lista adjunta). Si el lead pide hablar con humano o muestra frustracion, llena handoff_reason." Output: JSON validado contra el schema dinamico.

9) MERGE (Merge node) — combina output del extractor con { lead_id, agency_id, auto_actions, conversation_id } para tener todo el contexto en un mismo item antes de los Switch.

10) SWITCH/IF NODES EN PARALELO (uno por accion, leen campos del JSON):
    - IF name OR phone OR email OR budget OR zone present AND auto_actions.extract=true -> HTTP Request a edge function bot-actions/extract (mismo endpoint que la tool actual, solo cambia el caller).
    - IF stage_change present AND auto_actions.stage_change=true -> HTTP Request a bot-actions/stage.
    - IF qualified !== null AND auto_actions.qualify=true -> HTTP Request a bot-actions/qualify.
    - IF tags.length > 0 AND auto_actions.tag=true -> HTTP Request a bot-actions/tag.
    - IF note present AND auto_actions.note=true -> HTTP Request a bot-actions/note.
    - IF handoff_reason present -> HTTP Request a bot-actions/request_handoff (que internamente dispara Telegram + cambia handler='human').
    Cada IF chequea ademas idempotencia con lead.attributes_actuales para no re-escribir lo que ya esta (ej. si name ya existe igual, skip).

11) ERROR HANDLERS — cada rama del Switch tiene su Error Trigger: si la HTTP Request falla, escribe a logs.bot_action_failures con { lead_id, action, payload, error } y sigue. NO bloquea el flujo de conversacion (el reply ya se mando en paso 6).

12) AUDIT LOG (Postgres Insert al final) — registra { conversation_id, turn_n, extractor_output_json, actions_disparadas, latencia_total, model_used }. Esto es el activo de debugging: con un query SQL ves exactamente que decidio el extractor y que se ejecuto, sin reconstruir prompts ni leer logs de OpenAI.

DATOS QUE PASAN ENTRE NODOS: cada nodo recibe el item completo y enriquece. Al final del flujo, el item tiene { agency, lead, conversation, system_prompt, assistant_reply, extractor_json, actions_results }.

### Pros

- Sofia conversador se simplifica radicalmente: el system prompt baja de ~3000 a ~1800 tokens porque desaparecen los bloques de 'cuando usar cada tool / auto-actions permitidas'; el modelo ya no carga la carga cognitiva de decidir acciones mientras conversa — resuelve directamente las preocupaciones 1, 2 y 5 del founder
- Permite bajar Sofia de GPT-4 a gpt-4o-mini sin riesgo: sin tools, el modelo chico es suficiente para conversar bien (la dificultad de GPT-4 era el tool-calling, no la conversacion). Reduccion de costo de ~$0.04 a ~$0.0015 por turno conversador = ~25x mas barato
- Debugging trivial y auditable: el JSON del Information Extractor queda registrado en cada turno; ves EXACTAMENTE que decidio escribir antes de que se escriba. Hoy hay que reconstruir tool calls de logs de OpenAI; en C abris la ejecucion de N8N y lees el JSON literal
- Determinismo en la capa de escritura a DB: una vez que el JSON existe, los nodos IF/Switch+HTTP son 100% predecibles. Ya no hay 'a veces el agente no llama Stage_Tool' (preocupacion 4): si stage_change esta en el JSON, se ejecuta SIEMPRE; si no esta, no se ejecuta. El comportamiento es testeable con fixtures sin LLM
- Robustez multi-tenant mejora: el schema del extractor se compone dinamicamente desde agency.settings (etapas, tags permitidos, datos a capturar) — el extractor solo puede devolver valores validos para esa agencia, lo que ELIMINA bugs como 'el agente puso un stage que no existe en esa agencia'
- Desacopla reply de acciones en DB: Sofia responde al lead inmediatamente, las acciones (extract/stage/qualify/tag/note/handoff) se ejecutan en rama paralela. Si falla un INSERT a Supabase, el lead ya recibio respuesta — la conversacion no se rompe por errores de DB

### Cons

- Information Extractor agrega un segundo LLM call por turno: +1-2s latencia y +costo de tokens (aunque sea con gpt-4o-mini); el turno total pasa de ~3-6s a ~4-8s en el peor caso
- Menos flexibilidad para casos no anticipados: si el lead dice algo que no encaja en el schema (ej. 'mi hermano busca casa, no yo'), el extractor no captura la intencion y queda invisible para el sistema; el agente conversa pero no se ejecuta accion
- El schema del extractor se vuelve la nueva fuente de complejidad: agregar un campo nuevo (ej. tipo_propiedad) requiere editar schema + agregar IF/Switch + agregar nodo HTTP Request — mas trabajo que agregar una tool nueva al agente
- Doble fuente de verdad sobre el contexto: el agente conversa basado en memoria, el extractor analiza el ultimo turno aislado; pueden divergir (agente cree que ya tiene el telefono, extractor lo re-extrae y dispara update redundante)
- Information Extractor tambien puede fallar (hallucinations del JSON, campos mal tipados, valores fuera del enum) — no elimina el riesgo de fallo de LLM, lo desplaza a otro nodo con menos visibilidad porque ya no aparece en el chat
- Multi-tenant: el schema del extractor tiene que ser dinamico segun agency.settings (etapas del pipeline, tags permitidos, datos a capturar varian por agencia) — armar ese schema runtime es no-trivial y agrega un nodo Code mas

### Riesgos

- Cobertura del schema: si el founder agrega un caso de uso nuevo (ej. 'capturar interes en tipo_propiedad: casa/depto/lote') hay que tocar 3 sitios — Code node del schema, IF/Switch nuevo, HTTP Request nuevo. En el status quo bastaba con agregar una tool. Mitigacion: documentar el patron como skill 'agregar accion al hibrido determinista' (proceso replicable). Riesgo real en velocidad de iteracion los primeros 2 meses.
- Extraccion fantasma (false positives): el extractor con gpt-4o-mini puede alucinar valores. Ejemplo: el lead dice 'tal vez ~$200k' y el extractor pone budget=200000 con confianza. Hoy el agente puede preguntar 'lo confirmo?' antes de invocar Extractor_Tool; con C el extractor escribe directo. Mitigacion: agregar un campo 'confidence' al schema y solo ejecutar HTTP cuando confidence >= 0.8, o pasar el JSON por un check Code node que valide reglas duras (ej. budget tiene que aparecer como numero en el mensaje literal).
- Doble LLM call por turno: si hay un outage de OpenAI o rate limit, ahora hay dos puntos de fallo en serie. Mitigacion: el reply (paso 6) ya se mando antes de que falle el extractor; si el extractor falla, se loguea y el siguiente turno re-evalua el contexto acumulado en memoria — el sistema converge.
- El schema dinamico por agencia es el nodo critico oculto: si el Code node de paso 7 tiene un bug, todas las agencias se rompen al mismo tiempo. Mitigacion: tests unitarios sobre ese Code node con fixtures de 3-5 agency.settings reales antes de cada deploy; tratar ese nodo con la misma seriedad que una migracion de DB.
- Perdida de capacidad conversacional sutil: hoy el agente puede decir 'te asigno con Pedro' y simultaneamente llamar Assign_Tool — el mensaje al lead y la accion estan acopladas semanticamente. En C, Sofia puede prometer 'te asigno con Pedro' pero el extractor no extraer assigned_user porque no esta en el schema (los 7 tools del status quo incluian Assign_Tool pero el brief solo lista 7 campos sin assignment). Revisar el schema final para cubrir TODAS las acciones del status quo o aceptar conscientemente cuales se pierden.

### Implementacion

- **Nivel:** media
- **Razon:** Reuso el ~70% del workflow actual: Trigger, Resolve Agency, Resolve Lead, edge function bot-actions y su gate por auto_actions se quedan IGUAL. Lo nuevo (~30%): (1) quitar las 7 tools del LangChain Agent y simplificar el system prompt, (2) agregar Code node 'Componer Schema Dinamico' que es el unico punto realmente nuevo y no trivial porque el schema varia por agencia, (3) agregar Information Extractor node con prompt corto, (4) agregar 6 IF/Switch + 6 HTTP Request (mecanico, copy-paste de plantilla), (5) agregar Audit Log al final. El riesgo de implementacion vive en el Code node del schema dinamico — si la agencia cambia settings hay que invalidar cache o computar runtime cada turno. Tiempo estimado: 2-3 dias de un dev senior incluyendo testing del extractor con casos reales de las conversaciones grabadas (los hay que sirven como golden set).

### Costo y latencia (proponente)

- **Costo vs status quo:** 0.4x si Sofia migra a gpt-4o-mini para conversar + gpt-4o-mini para extraer (~$0.0015/turno vs ~$0.04 status quo con GPT-4). Si Sofia se mantiene en GPT-4 y solo el extractor usa gpt-4o-mini: 1.05x (~$0.042/turno, casi igual al status quo). El ahorro real viene de poder bajar Sofia a un modelo mas chico porque ya no decide tools.
- **Latencia vs status quo:** +1.0 a +1.5s en el camino critico observable por el lead, PERO solo si se mide hasta que se completan las acciones. Si se mide hasta el reply (que es lo que el lead siente), es -1 a -3s porque la rama de reply (Sofia gpt-4o-mini sin tools) corre en paralelo y devuelve en ~1-2s vs 3-6s del status quo con GPT-4 + 7 tools. Resumen: lead ve respuesta MAS RAPIDO (~2s vs ~4-6s), las acciones en DB se completan ~1.5s despues del reply. Para el founder esto es estrictamente mejor.

## Pipeline secuencial con LLM auditor mas chico

**Key:** `D-pipeline-auditor`

**Resumen:** "Arquitectura de doble LLM en pipeline secuencial: GPT-4 conversa SIN tools y responde al lead inmediatamente, luego gpt-4o-mini audita el turno (lead message + bot reply + historial + estado del lead) y devuelve JSON estricto con que tools invocar. Resuelve el problema de sobrecarga del agente unico y mantiene costo casi igual al status quo (gpt-4o-mini agrega ~3%), pero introduce dependencia de un segundo LLM para la capa de acciones — el auditor pequeno tiene que ser calibrado con cuidado para no fallar en decisiones criticas como Request_Handoff."

### Flujo propuesto

"FLUJO N8N NODO-POR-NODO:\n\n1. **Trigger YCloud Webhook** (Webhook node) — recibe POST de YCloud con mensaje entrante de WhatsApp. Payload: { from, to, text, message_id, timestamp }.\n\n2. **Resolve Agency** (Supabase node, SELECT) — lookup de la agency_id por phone_number_id de YCloud. Output: { agency_id, agency_name, agency_settings, bot_config }.\n\n3. **Resolve Conversation + Lead** (Supabase node, SELECT con upsert logica) — busca o crea conversation + lead. Output: { conversation_id, lead_id, lead_attributes, handler, stage }.\n\n4. **Gate Handler** (IF node) — si handler='human', cortar el flujo (no responder, el humano atiende). Si handler='bot', seguir.\n\n5. **Componer System Prompt Conversador** (Code node JS) — arma el prompt dinamico SOLO con bloques conversacionales: ## QUIEN SOS, ## SOBRE ESTE NEGOCIO, ## TONO, ## ETAPAS DEL PIPELINE (para contexto), ## DATOS YA CAPTURADOS (estado actual del lead). **OMITE intencionalmente** ## AUTO-ACCIONES PERMITIDAS y ## REGLAS sobre cuando llamar tools — el conversador NO sabe que existen tools. Output: { system_prompt_conversador }.\n\n6. **LangChain Agent Conversador (GPT-4)** — recibe system_prompt + Memory (Postgres) + ultimo mensaje del lead. **SIN tools conectadas.** Solo responde texto. Output: { bot_reply_text }.\n\n7. **Send WhatsApp Reply** (HTTP Request -> YCloud API) — manda bot_reply_text al lead INMEDIATAMENTE. Esto desacopla la respuesta del lead de la auditoria posterior — el lead recibe respuesta en ~3-6s sin esperar al auditor.\n\n8. **Persist Bot Message** (Supabase node, INSERT en messages) — guarda el mensaje del bot en la tabla messages para mostrarlo en el Inbox del CRM en tiempo real.\n\n9. **Componer Prompt Auditor** (Code node JS) — arma un prompt corto y enfocado para gpt-4o-mini. Incluye: (a) ultimo mensaje del lead (texto crudo), (b) respuesta del bot recien enviada, (c) ultimos 3-4 turnos de historial, (d) estado actual del lead (attributes, stage, tags), (e) ## AUTO-ACCIONES PERMITIDAS de bot_config, (f) lista de 7 tools disponibles con descripcion de 1 linea cada una, (g) reglas de decision concretas ('si el lead dio nombre/tel/email/presupuesto -> Extractor; si pidio hablar con humano explicitamente -> Request_Handoff; si menciono interes en zona X -> Tag; etc'). Output: { system_prompt_auditor }.\n\n10. **Information Extractor (gpt-4o-mini)** — usa el Information Extractor node de N8N con schema JSON estricto: { actions: [{ tool: 'Extractor'|'Stage'|'Qualify'|'Assign'|'Tag'|'Note'|'Request_Handoff', params: {...}, reason: string }] }. El node valida el schema automaticamente. Output: { actions: [...] } — puede ser array vacio si no hay nada que hacer.\n\n11. **Split Actions** (Split Out node) — si actions tiene items, los expande a items individuales para procesar en paralelo. Si array vacio, el flujo termina aca silenciosamente.\n\n12. **Switch por Tool** (Switch node, 7 ramas) — enruta cada action al endpoint correcto de bot-actions segun action.tool.\n\n13. **HTTP Request a bot-actions edge function** (7 nodos en paralelo, uno por rama del Switch) — llama al mismo edge function que hoy con el payload correspondiente. Headers: { Authorization: secret, agency_id, lead_id }. La edge function valida auto_actions.* gates igual que ahora.\n\n14. **Log Audit Trail** (Supabase node, INSERT en bot_audit_log) — registra: { turn_id, conversador_reply, auditor_actions, executed_at, latency_ms }. Critico para debugging y para medir si el auditor mini esta acertando.\n\n15. **(Async) Telegram Alert si Request_Handoff** — rama paralela que dispara solo si una de las actions fue Request_Handoff, manda mensaje a Telegram del agente.\n\n**Datos clave que viajan entre nodos:**\n- agency_id, lead_id, conversation_id (desde nodo 2-3 hasta el final)\n- Memory (Postgres chat memory de LangChain) — solo el conversador la lee/escribe\n- bot_reply_text — output del conversador, input del auditor + input del persist + input al lead\n- actions[] — output del auditor, drive el Switch + las 7 ramas de tools\n\n**Decision de arquitectura clave:** el Send WhatsApp Reply (nodo 7) ocurre ANTES del auditor (nodo 10). Esto significa que el lead ve la respuesta en latencia de 1 sola LLM call (la del conversador), y las tools se ejecutan en background sin bloquear UX. Si el auditor tarda 2s extra, el lead no lo nota."

### Pros

- Separa responsabilidades: conversador solo conversa (prompt mas corto, mas calibrable, menos tokens en cada call ~1500 vs ~3000), auditor solo decide acciones (prompt enfocado, schema JSON estricto). Resuelve directamente la preocupacion 'le estamos dando demasiada responsabilidad al agente'.
- El conversador sin tools es mucho mas predecible: GPT-4 sin tools tiene latencia mas estable (~2-4s vs 3-6s con tools) y no se distrae decidiendo si llamar algo.
- El auditor con Information Extractor + schema JSON estricto da validacion automatica de output — si el LLM devuelve algo invalido, N8N falla rapido y se puede loggear/reintentar sin escribir basura en DB.
- Send WhatsApp ANTES del auditor desacopla UX de la auditoria — el lead recibe respuesta rapida aunque el auditor tarde o falle. La conversacion no se rompe nunca por bug en tools.
- Costo casi igual al status quo (~3% mas) porque gpt-4o-mini es 30x mas barato que GPT-4 — el auditor agrega centavos por turno.
- Debugging mucho mas facil: separa 'que respondio el bot' de 'que acciones decidio el sistema' en dos artefactos independientes loggables. Permite medir accuracy del auditor de forma aislada (ground truth vs predicted actions).

### Cons

- Doble LLM call por turno: latencia se acumula (conversador 3-6s + auditor 1-2s = 4-8s end-to-end, antes de tool execution). En p95 puede tocar 10s y sentirse lento en WhatsApp.
- Dependencia del auditor pequeno: gpt-4o-mini puede ser inconsistente decidiendo cuando llamar Request_Handoff o Qualify (decisiones criticas de negocio). Si el auditor falla, las tools no se ejecutan aunque el conversador haya dicho lo correcto.
- El conversador no sabe que el auditor va a actuar despues -> puede prometer cosas (ej. 'te asigno con Juan') que el auditor no termina de ejecutar. Desincronizacion entre lo dicho y lo hecho.
- Costo del auditor no es trivial cuando se suma: ~$0.001 por turno extra x miles de conversaciones x N turnos = se nota en la factura mensual (no es despreciable como parece a primera vista).
- Tools como Extractor (captura nombre/tel/email) requieren ver el ultimo mensaje del lead, no la respuesta del bot -> el prompt del auditor tiene que recibir ambos (mensaje del lead + respuesta del bot + historial) -> mas tokens, mas complejidad de prompt.
- Debugging mas dificil: cuando algo falla hay que mirar dos LLM calls separados, dos prompts, dos sets de logs. El blast radius se duplica.

### Riesgos

- Auditor pequeno puede tener falsos negativos en tools criticas (no llamar Request_Handoff cuando deberia, no llamar Qualify cuando el lead dio toda la info). Mitigacion: few-shots concretos en el prompt del auditor + rule-based fallback para Request_Handoff via regex sobre el mensaje del lead ('quiero hablar con un humano|agente real|persona').
- Desincronizacion conversador-auditor: el bot puede decir 'te asigno con Juan' y el auditor decidir no llamar Assign_Tool (porque no lo ve como senial clara). Mitigacion: agregar al prompt del auditor la regla 'si el bot prometio una accion explicita en su respuesta, ejecutala'.
- Si el auditor falla (timeout, error 500, JSON invalido), las tools no se ejecutan ese turno. Mitigacion: dead-letter queue en una tabla bot_audit_failures + retry async + alerta. No es bloqueante para la conversacion (que ya respondio), pero hay que monitorearlo.
- El Information Extractor de N8N puede ser estricto con el schema — si gpt-4o-mini devuelve params con keys extras o tipos raros, el node falla. Mitigacion: schema permisivo (additionalProperties: true en params) + validacion post-hoc en Code node antes del Switch.
- Costo del auditor escala lineal con turnos: a 100k turnos/mes son ~$100 extra de gpt-4o-mini. No es problema ahora pero a escala de 10M turnos/mes son $10k/mes. Hay que medir con datos reales antes de descartar como insignificante.
- Prompt engineering del auditor es un trabajo continuo: cada vez que se agrega una tool nueva o cambia auto_actions config, hay que reescribir/recalibrar few-shots. No es plug-and-play.

### Implementacion

- **Nivel:** media
- **Razon:** Reutiliza el 80% del workflow actual (trigger, resolve agency, memory, send WhatsApp, edge function bot-actions sin cambios). Lo nuevo es: (1) separar el LangChain Agent conversador y quitarle las 7 tools, (2) construir el nodo Information Extractor con schema JSON estricto de 7 acciones, (3) construir el Switch + 7 HTTP Requests paralelas (vs hoy que es el agente quien las llama via tools). El cambio mas delicado es escribir el prompt del auditor con few-shots concretos para que decida bien cuando llamar cada tool — requiere iteracion con casos reales. Tiempo estimado: 2-3 dias de build + 1 semana de calibracion con conversaciones reales antes de produccion.

### Costo y latencia (proponente)

- **Costo vs status quo:** "1.03x (practicamente igual — el auditor mini agrega ~$0.001 sobre los ~$0.04 del conversador GPT-4; insignificante salvo a gran escala donde suma ~3% mensual)"
- **Latencia vs status quo:** "+0ms percibida por el lead (respuesta sale en el mismo tiempo que hoy, ~3-6s, porque el auditor corre DESPUES del send), pero +1-2s en latencia de tool execution (las acciones se aplican 1-2s mas tarde que hoy). Si el auditor corriera ANTES del send, seria +1-2s percibidos."

# Apendice B — Las 16 evaluaciones adversariales

Cada arquitectura fue juzgada por 4 lentes independientes. Los jueces fueron instruidos a "encontrar fallas, default a problemas si hay duda".

`blocker=true` significa que el juez identifico un problema que impide ir a produccion con escala objetivo.

## Status quo mejorado (1 agente, 7 tools)

### Lens: reliability [HIGH] BLOCKER

**Findings:**

- **SPOF en una sola llamada LLM no determinista: el LLM decide simultaneamente (a) que responder, (b) que tools llamar, (c) cuantas tools, (d) en que orden. Si la decision falla (ya reportado por el founder: 'a veces no llama las tools que deberia'), no hay safety net. Un prompt mejor reduce la frecuencia pero NO elimina el modo de falla. En produccion con cientos/miles de conversaciones, un 8-15% de fallas en tool-calling = decenas a cientos de leads con datos no capturados / no asignados / no escalados por hora pico.**
  - Impacto: Leads se quedan sin extraccion de presupuesto/zona, sin asignar a agente, sin handoff cuando piden humano. El CRM queda inconsistente con la realidad de la conversacion. Founder se entera por queja del agente humano que abre el lead y ve 'nada capturado' a pesar de que el lead dio toda la info. Erosion silenciosa de confianza en el bot.
- **No hay reintento ni fallback cuando OpenAI da error (rate limit 429, 500, timeout, schema-invalid tool_call). El workflow N8N por defecto propaga el error y mata la ejecucion del turno. Bajo carga (cientos de conversaciones simultaneas) los 429 de OpenAI son frecuentes. Tampoco hay circuit breaker: si OpenAI esta degradado, el bot sigue llamando y acumulando errores.**
  - Impacto: Mensaje del lead recibido pero nunca respondido. Lead percibe 'me dejaron en visto'. Sin retry queue ni dead-letter, el mensaje se pierde para siempre — Postgres tiene el mensaje del lead pero el bot nunca produjo respuesta. En pico esto puede ser 5-10% de los turnos invisible para el founder.
- **Memoria conversacional ilimitada en Postgres Chat Memory: a mayor numero de turnos por lead, mayor el contexto enviado al LLM. Sin truncado/resumen, conversaciones de 50+ turnos (comunes en inmobiliaria: ida y vuelta sobre propiedades) consumen 8k+ tokens solo en history, dejando poco room para el prompt sistema (4.5k+) — se acerca al limite practico de atencion efectiva de GPT-4 (~16k utiles antes de degradar). El nodo 'warm-up' que mete resumen breve es paliativo, no estructural.**
  - Impacto: Conversaciones largas degradan en calidad: el LLM 'olvida' lo que el lead dijo al inicio (lost-in-the-middle), repite preguntas (loop, ya visto por eso existe la skill bot-anti-loop-detector), o ignora reglas del prompt sistema porque quedan lejanas. Las conversaciones largas son justo las MAS valiosas (leads engaged). Esa cohort se rompe primero.
- **Tool execution sin idempotencia ni deduplicacion: si el LLM invoca Stage_Tool dos veces en el mismo turno (alucina double-call), o si N8N reintenta el turno por error transient, el lead se mueve 2 etapas en lugar de 1. Tampoco hay lock por lead_id: si dos mensajes del mismo lead llegan en rapida sucesion (cosa comun en WhatsApp: lead manda 3 audios seguidos transcritos), corren dos pipelines del Agent en paralelo, ambos leen el mismo state, ambos escriben — race condition clasica.**
  - Impacto: Lead salta etapas, queda asignado a dos agentes distintos, recibe dos respuestas contradictorias. En multi-tenant esto es peor porque cada agency tiene su propia logica de etapas y un salto puede activar automatizaciones downstream (telegram alert duplicada, asignaciones que disparan SLA). Bajo carga es probabilidad alta, no edge case.
- **Gate de auto_actions vive en bot-actions edge function, pero la decision de mencionar/no mencionar la tool en el prompt vive en N8N (Bloque 4). Drift garantizado: si la agency toggle auto_actions.assign=true via UI pero el cache del Resolve Agency node tiene la version vieja por TTL, el prompt no incluye Assign pero la edge function si la permite (o viceversa). Tambien: si el LLM IGNORA el bloque condicional y llama una tool no permitida, la edge function devuelve 403, pero el LLM ya gasto tokens y el lead vio un silencio raro mientras el agent reintentaba.**
  - Impacto: Configuracion inconsistente vista desde el lead. Agencies que pagaron por Assign no lo ven funcionar hasta que invalida cache. Errores 403 que el LLM no sabe interpretar y que pueden disparar respuestas raras al lead ('hubo un error, podes repetir?').
- **Bot-actions edge function es otro SPOF no mencionado en el analisis: 7 tools, todas llaman al mismo edge function. Si Deno cold-start (Edge Functions de Supabase tienen cold starts de 200-1500ms), el primer call del dia/region es lento. Si Supabase tiene incidente regional, el bot pierde TODAS las tools de golpe (no solo una). Sin health check ni circuit breaker, el agent sigue intentando, los timeouts se acumulan, y la latencia percibida por el lead se va a 15-20s.**
  - Impacto: Outage parcial de Supabase = outage total del bot. No hay degradacion graceful (ej. 'guardo la respuesta sin tools y reintento async'). El bot deja de capturar datos pero sigue conversando, generando estado divergente entre lo que el lead dijo y lo que el CRM sabe.
- **El nodo nuevo 'Log LLM Decision' (bot_turns) es la unica fuente de observabilidad propuesta, pero (a) no hay schema definido para 'tools_no_invocadas_evaluables' — ese campo requiere un segundo pass del LLM o reglas heuristicas que no existen, asi que va a quedar vacio, (b) no hay alerting sobre el log (founder se entera revisando manualmente), (c) si Postgres esta saturado, el INSERT del log puede fallar y silenciosamente perder telemetria justo cuando mas la necesitas (durante un incidente).**
  - Impacto: Observabilidad teorica, no operacional. Cuando algo falle en produccion, el founder va a abrir bot_turns y ver el dato bruto, pero sin alertas/dashboards no se entera proactivamente. Encima, debugging post-mortem incompleto si justo durante el incidente el log fallo.
- **Sin eval set automatizado pre-deploy. La mitigacion 'armar golden set de 30-50 conversaciones' esta listada como 'mitigacion' pero no como prerequisito. Iterar el Code Node 'Componer System Prompt' es 'minutos' segun el plan — eso es exactamente el escenario donde se rompen cosas en produccion porque nadie corrio el regression test. Y con prompt dinamico (depende de agency.settings + bot_config + auto_actions + pipeline_stages), el espacio de configuraciones a testear es combinatorio.**
  - Impacto: Cada iteracion del prompt es ruleta. Una agency rompe porque su pipeline_stages tiene una etapa con nombre raro que confunde a Stage_Tool, otra agency rompe porque tiene auto_actions.handoff=false pero los leads piden humano. Bajo escala (muchas agencies) la varianza explota. Sin eval set blockeante en CI/CD, el founder vive en modo bombero.
- **Recuperacion de fallos no esta diseñada. Si un turno falla a la mitad (ej. Extractor_Tool escribio attributes pero Stage_Tool fallo porque la edge function timeouteo), el estado queda parcialmente actualizado. No hay rollback ni reconciliacion. El siguiente mensaje del lead llega con state inconsistente y el LLM puede tomar decisiones sobre datos a medias.**
  - Impacto: State drift acumulativo. Leads con attributes pero sin stage avanzado, leads cualificados pero no asignados. El CRM se vuelve 'casi correcto pero no del todo' — el peor estado posible porque el agente humano confia en lo que ve.
- **Latencia bajo carga no esta modelada. El estimado '+0ms a +200ms' asume comportamiento del LLM independiente de carga, pero (a) OpenAI hace queueing en pico (rate-limit-aware backoff), (b) Supabase edge functions tienen concurrency caps, (c) N8N self-hosted en Easypanel con muchas ejecuciones simultaneas satura workers. Con cientos de conversaciones simultaneas el percentil 95 de latencia puede irse a 15-20s facilmente, no los 3-6s del estimado.**
  - Impacto: Lead siente al bot 'colgado'. WhatsApp tiene una expectativa de respuesta <10s para sentirse 'live'. Si el p95 se va arriba de eso, el lead manda mensajes nuevos mientras el bot procesa el anterior — y se desencadena el problema #4 (race condition por mensajes en rapida sucesion). Doble penalidad.

**Recomendacion del juez:** Esta opcion (A) NO es production-ready para 'cientos a miles de conversaciones simultaneas' con muchos clientes. Mejora marginal sobre status quo, pero deja intactos los modos de falla criticos: SPOF en una sola llamada LLM no-determinista, ausencia de retry/circuit-breaker/dead-letter, race conditions por mensajes paralelos del mismo lead, falta de idempotencia en tools, observabilidad sin alerting, sin eval set blockeante. Recomendacion concreta: usar esta opcion SOLO como puente de 2-3 sprints mientras se construye en paralelo C (hibrido determinista) o D (auditor con gpt-4o-mini). Antes de produccion real son OBLIGATORIOS (no opcionales): (1) idempotencia + lock por lead_id (Postgres advisory lock o cola por lead), (2) retry con backoff + dead-letter queue para turnos fallados, (3) eval set de 50+ conversaciones corriendo en cada cambio de prompt como gate de deploy, (4) circuit breaker sobre bot-actions edge function + degradacion graceful (responder al lead aunque las tools fallen), (5) truncado/resumen de memoria conversacional con cap duro de tokens, (6) alerting sobre bot_turns (tasa de tools fallidas, p95 latencia, errores 403/429) — no solo el log. Sin esto, el bot va a entrar a produccion y se va a romper silenciosamente con cohortes de leads especificas (conversaciones largas, leads que mandan multiples mensajes seguidos, agencies recien onboardeadas con config rara, ventanas de incidente parcial de Supabase/OpenAI).

### Lens: cost [HIGH]

**Findings:**

- **Multiplicador real es 1.3x-1.7x, NO 1.0x-1.3x como dice el documento. El estimado del founder subestima los few-shots. 7 tools x 2 ejemplos x ~150 tokens = 2.1k tokens, pero ademas suma anti-patterns (~50 tokens/tool x 7 = 350), trigger semantico (~80 tokens/tool x 7 = 560) y formato (~100 tokens). Total bloque 5 nuevo: ~3.1k tokens, no 2.1k. Sobre un prompt base de ~3k actuales, eso es +100% en input prompt, no +30-50%.**
  - Impacto: Con GPT-4 ($30/M input), prompt de ~6k tokens x N turnos por conversacion x miles de conversaciones = costo real puede ser 1.5x-1.8x, no 1.3x. En 10k conversaciones/dia con 8 turnos promedio cada una, eso son 80k turnos x ~6k input = 480M tokens input/dia = $14,400/dia solo input con GPT-4. Status quo seria ~$8,000/dia. Diferencia: $6,400/dia, $192k/mes en sobrecosto. Con miles de agencies esto no es viable economicamente.
- **El prompt CRECE con cada feature/regla/tool nueva y NUNCA decrece. El propio documento admite 'Prompt sigue creciendo: cada tool nueva o regla nueva = mas tokens'. No hay mecanismo de presupuesto de tokens, ni de poda automatica, ni de A/B test de versiones reducidas. En 6 meses con 3 verticals nuevos (no solo inmobiliaria) el prompt facil llega a 8-10k tokens base.**
  - Impacto: Costo escala lineal con features pero ingreso por cliente NO escala lineal. Margen unitario se degrada con el tiempo. En multi-tenant con cientos de agencies, esto significa que el cliente #500 cuesta mas servir que el #50 sin mejora de pricing. Trampa de margen clasica.
- **Conditional por auto_actions ahorra tokens, pero el ahorro es marginal en el caso promedio. Si la agency media tiene 5 de 7 tools habilitadas (Extractor, Stage, Qualify, Tag, Note suelen estar todas on; solo Assign y Handoff son opcionales), solo ahorra 2 tools x ~450 tokens = ~900 tokens. Eso es ~15% de ahorro en el caso optimista, no 30%+. Y en agencies premium con todas habilitadas, ahorro = 0.**
  - Impacto: El argumento de 'conditional por auto_actions reduce tokens irrelevantes — ahorro real, no marketing' esta sobrevendido. En el escenario realista de produccion con muchas agencies activas, el ahorro promedio es del 10-15%, no compensa el +100% del bloque 5.
- **Memoria de Postgres Chat Memory mete TODO el historial en el contexto en cada turno (o ventana movil sin resumen). Con conversaciones de 20+ turnos (lead que tarda dias en decidir), el input por turno se infla a 8-12k tokens facil. Sumado al prompt nuevo de 6k base = 14-18k tokens input por turno en conversaciones largas.**
  - Impacto: GPT-4 cobra $30/M input. Una conversacion de 30 turnos con prompt grande podria costar $0.50-$1.50 SOLA. Con miles simultaneas en pico, esto explota. El documento no menciona estrategia de resumen/compactacion de memoria, lo cual es critico para el modelo de costo.
- **El plan B 'switchear a gpt-4o-mini para ahorrar 30x' es presentado como mitigacion, pero no se sabe si pasa el eval con prompt MAS LARGO (que es justo el que esta opcion propone). Modelos pequenos son mas sensibles a prompts largos — 'lost-in-the-middle' es peor. Si gpt-4o-mini NO pasa el eval con few-shots por tool, te quedas con GPT-4 y el costo explota. El plan B es un wishful thinking sin validar.**
  - Impacto: Si la asuncion de gpt-4o-mini falla, el founder esta atrapado: prompt mas largo + modelo caro + no hay ahorro de arquitectura. El upside (30x cheaper) esta condicionado a que el modelo barato funcione con el prompt nuevo — y la opcion C/D (hibrido determinista) tendria MEJORES chances con gpt-4o-mini porque divide carga cognitiva.
- **Output tokens no se discuten. El LLM en un solo turno hace: (a) respuesta al lead, (b) 0-N tool calls con args estructurados, (c) potencialmente tool results re-procesados. Cada tool call son ~50-200 tokens output. Con 7 tools y prompt que invita a llamarlas, el output por turno puede ser 200-600 tokens (vs ~100 status quo).**
  - Impacto: Output cuesta 4x mas que input ($60/M GPT-4). Si output sube de 100 a 400 tokens promedio, eso son 300 tokens extra x $60/M = $0.018 extra por turno. En 80k turnos/dia = $1,440/dia extra solo en output. El documento solo dice 'output similar' sin justificarlo.
- **Logging estructurado (nodo bot_turns) es buena idea pero NO es gratis: cada turno persiste system_prompt_hash, tools_invocadas, tokens_in, tokens_out, latency_ms — ese INSERT a Postgres en cada turno x miles de conversaciones simultaneas suma carga DB y costo storage. No es bloqueante pero hay que dimensionarlo. Tampoco se menciona retention policy.**
  - Impacto: En 80k turnos/dia, ~30M turnos/ano. Tabla bot_turns crece exponencial. Si no hay particion/archivado, queries de debugging se vuelven lentas a los 3-6 meses. Costo Supabase Postgres tier sube. No es un blocker de cost del LLM en si, pero suma al TCO real.
- **No hay mencion de prompt caching (OpenAI lo soporta desde 2024 — descuentos de hasta 50% en tokens cacheados que se repiten >1024 tokens). El bloque estatico del prompt (## QUIEN SOS, ## CUANDO USAR CADA TOOL con few-shots, ## ETAPAS, ## REGLAS) deberia ser cacheado. Si se ordena el prompt con estatico ARRIBA y dinamico ABAJO, se cachean ~4-5k tokens.**
  - Impacto: Oportunidad de ahorro 30-50% en input desaprovechada. Con prompt caching bien implementado, el +100% input nominal se vuelve +30-40% efectivo. El documento NO menciona esto, lo cual sugiere que ni siquiera estan considerando esta optimizacion obvia. Esto es ahorro real, no especulativo, y la opcion A lo necesita SI o SI para ser viable a escala.

**Recomendacion del juez:** El estimado de costo del documento (1.0x-1.3x) esta optimistamente sesgado — el numero realista es 1.5x-1.8x sin prompt caching, 1.1x-1.3x CON prompt caching bien implementado. Antes de aprobar esta opcion como path a produccion, exigir: (1) prototipo del prompt completo medido en tokens reales (no estimado) con un sample de 20 conversaciones largas, (2) validar gpt-4o-mini con prompt nuevo en eval set ANTES de comprometerse — si no pasa con >90% accuracy, esta opcion no es viable economicamente a escala, (3) implementar OpenAI prompt caching reordenando estatico arriba/dinamico abajo (no es opcional, es requisito para que la matematica cierre), (4) estrategia de compactacion de memoria conversacional (resumen cada N turnos) — sin esto las conversaciones largas explotan, (5) cap duro de tokens output por turno (max 2 tool calls) para controlar costo de output. Si estos 5 puntos se cumplen, costo es manejable (~1.2x status quo). Si no, esta opcion es trampa de margen a 6 meses vista — la opcion C (hibrido determinista con Information Extractor) tiene mejor perfil de costo porque saca decisiones del LLM caro y las mete en logica n8n gratis.

### Lens: latency [MED]

**Findings:**

- **Prompt mas largo = mas tokens input = mas latencia de OpenAI. El propio doc admite +50-150ms por turno solo por procesamiento del prompt expandido. Con few-shots de 7 tools (~2.1k tokens extra) sobre un prompt ya de ~3k, estas en ~5k tokens input. GPT-4 con 5k input + 200 output = 3-5s solo de inferencia, antes de tools.**
  - Impacto: Baseline de respuesta sube. Si el lead esperaba 3s, ahora espera 3.5-4s. Solo. Antes de cualquier tool call.
- **Tool calls en serie dentro del Agent node: cada tool invocada hace HTTP a bot-actions edge function (~200-400ms cada una segun el propio doc). El LangChain Agent de N8N, cuando el LLM pide varias tools en un turno, las ejecuta y DESPUES re-invoca al LLM con los resultados para componer la respuesta final. Eso es: LLM call 1 (decide tools) + N tool calls + LLM call 2 (compone respuesta) = doble inferencia.**
  - Impacto: Turno tipico con 2 tools (Extractor + Stage) = 2 LLM calls (3-5s c/u con GPT-4) + 2 tool calls (~600ms) = 7-11s percibidos. El propio doc reconoce 8-10s con 3 tools. Ya esta en el limite de lo aceptable para WhatsApp.
- **Nodo nuevo 'Log LLM Decision' agrega latencia operativa antes de Send WhatsApp. Aunque chico (~50-150ms para un INSERT a Supabase via Postgres node), esta en el path critico ANTES de que el lead reciba el mensaje. Deberia ir despues del Send o en paralelo, pero el doc lo pone como nodo 8 antes del 9 (Send WhatsApp).**
  - Impacto: Suma 100-200ms innecesarios al tiempo percibido del lead. Facil de arreglar (mover despues de Send), pero como esta descrito hoy esta mal.
- **Carga inicial: nodos 2-5 (Resolve Agency, Resolve Lead, Gate Handler, Load History) son 4 queries a Postgres en serie ANTES de llegar al LLM. Cada query Supabase desde N8N self-hosted (Easypanel) tipicamente 50-150ms por la red. 4 queries serie = 200-600ms de overhead pre-LLM.**
  - Impacto: Antes de que el LLM siquiera empiece, ya pasaron 200-600ms. Sumado al LLM (3-5s) + tools (600ms-1s) + Send WhatsApp (~300ms) + Realtime (~100ms) = 4.2-7s base, sin contar el doble LLM call por tools.
- **No hay mitigacion para el caso peor (3+ tools en un turno). El doc lo identifica como riesgo ('cap max 2 tools por turno via prompt rule') pero esa regla es soft — el LLM puede ignorarla, especialmente GPT-4o-mini con menos adherencia a instrucciones. Sin hard limit a nivel N8N o bot-actions, un turno con 4 tools = 4 LLM calls + 4 tool calls = 15s+ facilmente.**
  - Impacto: Outlier tail latency. P95 de respuesta puede superar 10s en conversaciones reales donde el lead suelta 3 datos juntos (nombre + presupuesto + zona) y el LLM dispara Extractor + Stage + Tag + Note.
- **GPT-4 como default sigue siendo lento. El doc menciona switch a gpt-4o-mini como Plan B pero NO como parte del scope de esta opcion. Mientras se quede en GPT-4, todo turno tiene baseline 3-6s. Multi-tenant con cientos de conversaciones simultaneas: si rate limit de OpenAI pega, latencia se dispara (cola de requests).**
  - Impacto: Bajo carga (escala objetivo del founder: cientos/miles simultaneas), rate limits de OpenAI tier actual pueden meter delays adicionales de 1-5s en P99. La arquitectura no tiene buffer ni fallback (ej. cola con QStash, que se descarto).

**Recomendacion del juez:** No es blocker de latencia por si solo — la arquitectura es esencialmente la misma que hoy, asi que si hoy funciona en pruebas, manana tambien. Pero hay 3 cosas que SI o SI hay que hacer antes de produccion: (1) Mover 'Log LLM Decision' DESPUES de Send WhatsApp (o en paralelo via N8N branch), nunca en path critico — fix de 5min. (2) Switchear a gpt-4o o gpt-4o-mini con el eval set; GPT-4 es demasiado lento para WhatsApp a escala, y el founder ya lo identifico como Plan B obligatorio — esto baja baseline a 1-2s y deja margen para tools. (3) Hard cap en N8N (no en prompt) de max 2 tools por turno: agregar un If node despues del Agent que detecte si tool_calls.length > 2 y trunque, o limitar a nivel de Agent config. Si NO se hacen estos 3 fixes, P95 va a superar 10s en produccion con carga real y leads se van a quejar. Con los 3 fixes, esta opcion es viable para latencia (P50 ~2-3s, P95 ~5-7s). Riesgo de tail latency persiste sin observabilidad en latency_ms de bot_turns — monitorear desde dia 1.

### Lens: maintenance [HIGH]

**Findings:**

- **Debug surface concentrado en un solo Code Node + un solo LLM turn. Cuando un cliente reporte 'el bot no llamo Assign cuando deberia', el founder tiene que: (1) ir a N8N executions, (2) abrir el run especifico, (3) inspeccionar el output del Code Node 'Componer System Prompt' (string de 4500 tokens), (4) leer ese prompt completo para entender que vio el LLM, (5) abrir bot_turns y ver tools_no_invocadas_evaluables (campo que requiere que el LLM auto-reporte que tool *considero*, lo cual es inferencia subjetiva del modelo, NO un log determinista). En 3 meses el founder no va a recordar que bloque del prompt rige que comportamiento.**
  - Impacto: MTTR (mean time to resolution) por bug de tool-call va a ser horas, no minutos. Con muchos clientes reportando casos en paralelo, esto es insostenible. Sin un decision trace estructurado real ('input -> regla aplicada -> tool elegida'), debuggear el LLM es leer tea leaves.
- **Agregar una tool nueva NO es 'editar un archivo'. Es un cambio cross-file que toca minimo 5 lugares: (1) edge function bot-actions (agregar el action handler + RLS check), (2) workflow N8N (agregar el Tool node + cablearlo al Agent), (3) Code Node 'Componer System Prompt' (agregar bloque condicional en Bloque 4 segun auto_actions + bloque 5 con few-shots + anti-patterns), (4) tabla agencies.auto_actions (agregar el flag), (5) tabla bot_turns (los campos tools_invocadas[] crecen sin schema explicito). El founder tiene que mantener mentalmente la consistencia de los 5. Sin un registry central de tools, agregar la 8va y 9na tool va a ser cada vez mas caro.**
  - Impacto: La promesa de 'iterar rapido editando un Code Node' es falsa para el caso comun (tool nueva). Solo es rapido para reescribir prompt EXISTENTE. La complejidad cognitiva crece O(tools) en cada cambio.
- **El prompt es construido dinamicamente desde 4 fuentes (agency.settings, agency.bot_config, agency.auto_actions, agency.pipeline_stages, agency.lead_attributes_schema) + N hardcoded blocks en el Code Node. No hay forma de hacer 'diff' del prompt efectivo entre dos agencies, ni de saber cual de las 4 fuentes movio el comportamiento cuando algo cambia. Si la agency A funciona y la agency B no, el founder no puede comparar facilmente — tiene que reproducir 2 prompts completos a mano y diffearlos.**
  - Impacto: Onboarding de cada agency nueva = riesgo de regresion silenciosa. Multi-tenant amplifica esto: 50 agencies = 50 prompts efectivos distintos, ninguno versionado, ninguno comparable. No hay 'snapshot' del prompt que se uso en el turno X.
- **El nodo 'Log LLM Decision' que se vende como mitigacion tiene un problema fundamental de maintenance: el campo tools_no_invocadas_evaluables[] requiere que el LLM auto-reporte que tools considero pero no llamo. Eso es inviable — el LLM no tiene introspeccion confiable de su propio razonamiento. En la practica este campo va a quedar vacio o ser ruido, dejando al founder con tools_invocadas[] como unica senal, que es lo que ya tiene hoy implicitamente.**
  - Impacto: El supuesto 'debugging con data' es marketing. Sin un audit step explicito post-turn (un segundo LLM o reglas deterministas que evaluen 'segun esta conversacion, debio llamar X?'), bot_turns es solo logging de outputs, no de decisions. Es lo mismo que mirar el output final con mejor formato.
- **Few-shots embebidos en el Code Node string-template son un anti-pattern de maintenance. 7 tools x 2 few-shots = 14 fragmentos de texto curados a mano, mezclados con logica de armado de prompt, todo en un solo Code Node JavaScript. No hay test runner para validar que un cambio en el few-shot de Stage_Tool no rompe Extractor_Tool. No hay separacion entre 'data del prompt' y 'logica de composicion'. Cuando llegue el momento de agregar 2 verticales mas (no solo inmobiliaria), o este Code Node se vuelve un God Object de 1000 lineas, o se duplica por vertical (peor).**
  - Impacto: El golden eval set que mencionan en risks es OBLIGATORIO, no opcional, y la propuesta lo trata como nice-to-have. Sin eval set + sin separacion datos/logica, en 3 meses iterar el prompt va a sentirse como editar config de Apache en 2010.
- **Volver en 3 meses con esta arquitectura: el founder abre el workflow N8N y ve un Agent node con 7 tools cableadas, sin nombres semanticos del *cuando* (solo *que*). Tiene que abrir el Code Node, leer 200+ lineas de string template, mapear mentalmente que bloque del prompt rige que tool, y entender el orden de prioridad implicito. NO hay un mapa visual de 'estos son los triggers semanticos por tool'. La logica esta enterrada en prosa, no en estructura.**
  - Impacto: El sistema deja de ser editable por el founder solo y empieza a requerir un onboarding de medio dia para cualquier dev nuevo. Bus factor = 1. Para un SaaS multi-tenant en produccion eso es un riesgo de continuidad real.
- **Cuando un caso de produccion falle (lead quemado, bot no escalo a humano), el debugging path requiere correlacionar: ejecucion N8N + tabla bot_turns + tabla messages + tabla lead_events + edge function logs de bot-actions + memoria postgres del Agent. Son 6 fuentes de truth en 3 sistemas (N8N, Supabase DB, Supabase Edge logs). No hay un trace_id que los una. Sin trace correlacionado, reproducir un bug de un cliente real es trabajo de detective.**
  - Impacto: Con 1 agency en pruebas esto duele un poco. Con 50 agencies en produccion y SLAs implicitos (lead WhatsApp espera <10s), no hay forma de hacer postmortem rapido. Esto es el bottleneck real cuando llegue el primer caso de 'el bot perdio un cliente VIP'.

**Recomendacion del juez:** No mergear esta opcion como 'la mejora' sin agregar 3 piezas de maintenance ANTES de produccion real (el founder dice 1 mes): (1) Trace_id correlacionado end-to-end: generar un uuid en el webhook YCloud y propagarlo por N8N -> bot_turns -> edge function logs -> messages. Permite reconstruir un turno completo con UNA query. (2) Tool registry como tabla Postgres (tools_catalog: name, description, few_shots_jsonb, anti_patterns_jsonb, schema_jsonb) en vez de string-template en Code Node. El Code Node solo arma el prompt leyendo de la tabla. Agregar tool nueva = INSERT, no editar JS. Diff entre agencies = SELECT. (3) Golden eval set obligatorio (no opcional): 30-50 conversaciones con tools esperadas, corrido como N8N workflow separado pre-merge. Sin esto, el riesgo de regresion silenciosa hace inviable iterar el prompt en produccion. Si estas 3 piezas no se agregan, esta arquitectura A es deuda de mantenimiento desde el dia 1, no una mejora. La opcion C (hibrido determinista con Information Extractor) tiene mejor perfil de maintenance porque el JSON validado por schema es debuggeable per se — no requiere inferir que penso el LLM.

## Multi-agente especializado (conversador + analista)

### Lens: reliability [HIGH] BLOCKER

**Findings:**

- **Race condition estructural en modo paralelo (recomendado en la propuesta): el reply al lead sale ANTES de que el analista escriba a DB. Si el lead responde en <2s (comun en WhatsApp cuando esta enganchado), el siguiente turno lee estado stale (stage viejo, attributes sin actualizar, qualified=null) y el conversador hace preguntas que ya estaban contestadas o vuelve a pedir datos. No es teorico: en inmobiliario el lead muchas veces responde con burst de 2-3 mensajes seguidos ('ok', 'mira', 'mi presupuesto es 150k').**
  - Impacto: Conversaciones que se sienten amnesicas y rotas — el bot pregunta el presupuesto despues de que el lead lo dio. A escala (cientos de conversaciones simultaneas), esto pasa varias veces por dia por agencia. Imposible de reproducir en testing porque depende del timing exacto del lead.
- **El analista NO tiene memoria conversacional propia (es stateless por turno). Eso significa que cada decision de tool-call depende 100% de que el composer del prompt incluya el lead_state actualizado y los ultimos 6 turnos correctos. Cualquier bug en el composer (falta serializar un campo, off-by-one en los turnos, lead_state stale por la race condition anterior) hace que el analista decida a ciegas. Y como el output del analista 'se ignora' (solo importan los side effects), no hay forma facil de saber QUE vio cuando decidio mal.**
  - Impacto: Cuando el analista falla, debugging requiere reconstruir el input exacto desde logs. Si bot_decisions_log no captura el input completo del turno (no esta especificado que lo haga, solo guarda tools_invoked + reasoning), el founder va a estar ciego ante el patron de fallas.
- **Doble punto de fallo en la cadena: timeout/rate-limit/parser-error del conversador OR del analista degradan el sistema. OpenAI tiene rate limits por org y por modelo; gpt-4o-mini tiene su propio bucket distinto a gpt-4-turbo. Con cientos de conversaciones simultaneas en pico, el analista (mini) puede saturar su bucket mientras el conversador (gpt-4) esta OK — o viceversa. No hay circuit breaker ni fallback descrito. Si el analista timeoutea, el reply ya se mando pero las acciones de CRM no ocurrieron y nadie se entera salvo que se mire el log.**
  - Impacto: Fallos silenciosos: el lead recibe respuesta, parece que todo OK, pero el stage no avanzo, no se asigno, no se capturo el email. El founder solo descubre el problema cuando un agente humano pregunta 'donde estan los leads de hoy?'.
- **Desincronizacion semantica entre conversador y analista no se resuelve con few-shots. El conversador puede usar lenguaje natural ambiguo ('ya le aviso a alguien del equipo', 'te confirmo en un momento', 'dejame revisar') que NO es literal 'paso a humano'. El analista mini (gpt-4o-mini) tiene capacidad limitada de inferencia pragmatica vs GPT-4 — por algo cuesta 30x menos. La regla 'si bot_reply contiene X, llama tool Y' es fragil: el conversador GPT-4 puede expresar la misma intencion de 50 formas distintas.**
  - Impacto: Falsos negativos en Request_Handoff y Assign — el conversador promete cosas que el analista no detecta, y el lead queda esperando una accion humana que nunca se dispara. En inmobiliario, un handoff perdido = lead frio = comision perdida. Critico para el value prop del producto.
- **Tools con efectos secundarios irreversibles (Request_Handoff dispara Telegram, Assign notifica al user) ejecutadas por un modelo barato (gpt-4o-mini) con menos precision. La propuesta menciona 'score de confianza minimo o segundo paso de validacion' como mitigacion pero NO esta implementado en el flujo de 11 nodos. Sin ese gate, cada falso positivo del analista = notificacion ruidosa al equipo humano.**
  - Impacto: El equipo humano deja de confiar en las alertas de Telegram (cry-wolf effect). Cuando una alerta legitima llega, se ignora. Esto destruye el unico mecanismo de escalacion del sistema.
- **No hay idempotencia ni retry strategy descrita. Si el N8N workflow falla entre el nodo 9 (analista) y el nodo 10 (log), o entre cualquier tool-call del analista y el siguiente, no esta claro como recupera. N8N reintenta el workflow desde el nodo fallado? Si el analista ya llamo Stage_Tool y falla Assign_Tool, el reintento vuelve a llamar Stage_Tool? bot-actions edge function tiene idempotencia por turn_id? No esta especificado.**
  - Impacto: Bajo carga, los retries de N8N (defaults o configurados) pueden duplicar tool-calls: doble stage change, doble assign, doble nota, doble alerta de Telegram. Multiplicado por miles de turnos/dia.
- **El composer del prompt del analista incluye 'ultimos 6 turnos de memoria' — pero la memoria Postgres del CONVERSADOR es la fuente. Si el conversador todavia no escribio el turno actual a memoria cuando el composer corre (timing depende de como LangChain Memory persiste — algunos backends son lazy), el analista ve N-1 turnos. Ademas, 6 turnos puede ser insuficiente en conversaciones largas donde el dato critico (presupuesto, intencion de compra) se menciono en el turno 8.**
  - Impacto: Decisiones del analista basadas en contexto incompleto. Captura tardia o nula de attributes que se mencionaron hace 7+ turnos. El status quo con 1 agente y memoria continua no tiene este problema.
- **El plan de calibracion ('test suite de turnos sinteticos') es vago y NO es parte de la implementacion. En 2-3 dias de desarrollo + 3-5 dias de calibracion no entra construir un harness de evaluacion real con conversaciones de produccion etiquetadas. Sin eso, ir a produccion con 'muchos clientes' es disparar a ciegas.**
  - Impacto: Sin metricas de tool-call accuracy/precision/recall ANTES de produccion, el founder no sabe si la arquitectura B es mejor que A hasta que clientes se quejen. Demasiado tarde.

**Recomendacion del juez:** No ir a produccion con arquitectura B en su forma actual. Tres bloqueos minimos que hay que resolver antes de considerarla: (1) Decidir SERIAL ESTRICTO no opcional — el modo paralelo introduce una race condition que en inmobiliario (bursts de mensajes del lead) va a manifestarse multiples veces por dia por agencia. La latencia extra de 1-2s es aceptable; conversaciones rotas no lo son. (2) Implementar idempotencia en bot-actions edge function via turn_id como unique key — sin esto, cualquier retry de N8N duplica side effects criticos (Telegram, Assign). (3) Gate de confianza para tools irreversibles (Handoff, Assign): el analista mini debe devolver score explicito y un nodo N8N condicional rechaza ejecuciones <0.8 — o esas tools se quedan en el conversador GPT-4. Adicionalmente, antes de declarar B vs A vs C, construir harness de evaluacion con 50-100 conversaciones reales etiquetadas de Sofia v6 (status quo) y correr las 4 arquitecturas contra el mismo set midiendo tool-call accuracy + latencia + costo. Sin ese baseline empirico, esto es teologia. Si el founder tiene 1 mes para produccion real, mi recomendacion para reliability es opcion C (hibrido determinista con Information Extractor) — quita al LLM del path de decision de tools criticas y deja al agente solo para conversar. Es la unica arquitectura donde 'si el LLM se equivoca' no rompe el CRM, solo rompe el reply individual.

### Lens: cost [HIGH]

**Findings:**

- **El multiplicador 1.3x esta subestimado. La arquitectura no solo agrega una LLM call mas - duplica el contexto cargado. El analista recibe lead_msg + bot_reply + ultimos 6 turnos + lead_state como user_input, mas un system prompt de 1200-1500 tokens. Eso son ~2000-2500 tokens de input por cada turno del analista, ADEMAS de los ~1500-1800 del conversador. Status quo real (con memoria) son ~3000-3500 tokens input por turno. Arquitectura B: ~3500-4500 tokens input totales (conversador ~1800 + analista ~2300). El input crece 30-50%, no se reduce.**
  - Impacto: La narrativa de '40% mas chico cada prompt' confunde input total con prompt individual. El costo real input-side sube, no baja. Solo el output baja porque el conversador genera texto y el analista genera tool_calls breves.

Arquitectura B con conversador GPT-4 + analista mini: conversador 1800 in + 200 out = $0.024; analista 2300 in + 150 out @ mini = $0.00043. Total ~$0.0244. ES MAS BARATO QUE EL STATUS QUO, no mas caro. El estimado del founder (~$0.05) esta inflado ~2x.**
  - Impacto: El framing 'duplica LLM calls = duplica costo' es falso porque el segundo call es 60-70x mas barato. La lens cost en realidad FAVORECE B sobre status quo si analista=mini. El problema no es el costo, es que el estimado original esta mal calculado y va a llevar al founder a descartar B por una razon que no aplica.

  - Impacto: Si el founder calcula con 50% de cache hit en ambos lados va a sub-estimar costo del analista en 30%. A escala importa: la diferencia entre 50% y 20% de cache hit en 80k turnos/dia son ~$200-400/dia.

A escala (80k turnos/dia) son 160k queries/dia adicionales a Supabase. En el plan Pro de Supabase no rompe, pero suma latencia (50-150ms cada una) y carga al pool de conexiones. No es 'costo de tokens' pero es costo operativo que la lens no contempla.**
  - Impacto: Cost lens ampliado a 'costo total operativo' empeora B. Tokens bajan, queries DB suben. A 1000+ agencias concurrentes el pool de Supabase puede saturarse antes que el budget de OpenAI.

El founder esta evaluando B vs status quo sin ver que C cuesta lo mismo que B pero elimina el riesgo de tool-calling mal calibrado del analista.**
  - Impacto: El analisis de lens cost para B es incompleto si no se compara contra C. B se ve bien aislada, pero contra C pierde porque C no tiene el riesgo binario del modelo del analista.

**Recomendacion del juez:** No es blocker por costo - de hecho B con analista=gpt-4o-mini es comparable o mas barata que el status quo. PERO el estimado original (1.3x-2x mas caro) esta mal calculado y va a llevar a decisiones erradas. ### Lens: latency [HIGH] BLOCKER

**Findings:**

- **El modo 'paralelo' que vende la arquitectura NO es paralelo real en N8N. El LangChain Agent node es sincrono y bloqueante — para que el nodo Send WhatsApp dispare antes de que termine el analista, hay que hacer split del flujo, lo cual en N8N requiere un nodo Execute Workflow async (+100-500ms) o un Webhook auto-llamado. El documento asume que con solo mover el orden de nodos ya es paralelo, y eso es falso. En la practica el flujo termina siendo serial encubierto.**
  - Impacto: La latencia 'paralela' (2-4s) que se promete NO se va a cumplir con la implementacion descrita. El lead va a esperar conversador + analista en serie = 4-8s tipicos, picos a 10-15s con GPT-4 + cold start de tools. Cruza el umbral de 'se siente raro' que el founder marco como rojo.
- **Status quo (1 agente GPT-4 con 7 tools) ya esta en 3-6s segun el propio documento. Sumar OBLIGATORIAMENTE una segunda LLM call (analista) garantiza minimo +1.5-3s adicionales. En picos reales con OpenAI (rate limits, cold paths del modelo, retries) cada call puede saltar a 8-12s. Dos calls encadenadas = riesgo real de pasar 15-20s en p95.**
  - Impacto: p95 latency se va a romper. WhatsApp Business no tiene timeout duro de respuesta, pero el lead que espera >10s sin ver 'escribiendo...' asume que el bot esta muerto y manda otro mensaje, generando race conditions que el propio doc admite en cons #2 y risks #2.
- **Cada agente nuevo agrega overhead operacional de N8N que el doc ignora: composer Code node (~50-150ms), nodo LangChain Agent setup/teardown (~200-400ms por instancia), Postgres Memory query (~100-300ms — el analista no usa memory pero el conversador si), Supabase consultas extra para armar el contexto del analista (lead_state, ultimos 6 turnos = otra query ~150-400ms), Insert en bot_decisions_log (+50-150ms). Suma realista: +500ms a +1.2s de overhead N8N puro, ANTES de contar la LLM call extra.**
  - Impacto: El estimado optimista de '+1.5s' subestima por factor 2x. Latencia real esperada: +3-5s sobre status quo en modo serial, no +2.5s. En multi-tenant con cientos de conversaciones simultaneas, N8N self-hosted en Easypanel va a empezar a hacer queue de ejecuciones y la latencia se degrada no-linealmente.
- **El analista corre DESPUES del reply en modo paralelo. Eso significa que datos criticos del lead (nombre, presupuesto, zona) que se debieron capturar en el turno N solo se persisten al final del turno N. Si el lead manda mensaje en turno N+1 antes de que el analista del turno N termine, el conversador del N+1 lee estado stale y vuelve a preguntar lo mismo. Para el lead se siente como un bot lento Y olvidadizo — peor que un bot solo lento.**
  - Impacto: Latencia percibida no es solo segundos por turno, es 'turnos desperdiciados'. El doc admite en cons #6 que la captura puede tomar 2-3 turnos en vez de 1. Si cada turno tarda 4-6s, el ciclo de calificacion completo se va de 30s (status quo) a 60-90s. Inaceptable para escala de cientos de leads concurrentes.
- **OpenAI prompt caching (mitigacion #3 de costo) NO ayuda con latencia tanto como vende — el cache hit ahorra ~50% de tokens de input pero solo ~10-30% de latencia segun docs de OpenAI, porque el cuello sigue siendo TTFB y generacion de output. Y el cache solo aplica con prefijos identicos >1024 tokens, lo cual rompe la dinamica del prompt multi-tenant (cada agency tiene bloques distintos). El analista con prompt dinamico por agencia va a tener cache hit rate bajo en picos.**
  - Impacto: La ventaja de costo se diluye Y la latencia no baja. Pasar a gpt-4o-mini en analista ayuda mas a latencia (~30-50% mas rapido que GPT-4) pero introduce el riesgo de cons #1 (analista debil no detecta seniales).
- **El doc no mide latencia de la edge function bot-actions bajo carga concurrente. Hoy con 1 agente, una tool call dispara 1 invocacion de bot-actions. Con multi-agente, el analista puede disparar 0..N tools — si dispara 3-4 en un turno (extractor + stage + tag + note), son 3-4 calls a la edge function en cascada (LangChain las hace secuencial por defecto en el Agent node de N8N), agregando 200-600ms por tool. Combinado con el resto: turno completo puede pasar 12s.**
  - Impacto: Latencia compuesta no medida. Bajo carga real con miles de conversaciones, los Supabase edge functions tienen cold starts y rate limits que el doc no contempla.

**Recomendacion del juez:** No avanzar con arquitectura B (multi-agente conversador + analista) por la lente de latencia. Tres caminos en orden de preferencia: (1) Hacer pruebas de latencia REALES con status quo (Opcion A) antes de duplicar LLM calls — medir p50/p95/p99 con 10-20 conversaciones simultaneas en N8N de Easypanel actual; si p95 ya esta en 6-7s, agregar otro agente lo lleva a 10-12s y se rompe. (2) Evaluar seriamente Opcion C (Hibrido determinista): 1 agente conversa + Information Extractor structured-output + nodos N8N condicionales. Information Extractor es UNA llamada LLM con schema validado, no agrega segunda llamada agentica, y los nodos condicionales son zero-latency. Esta arquitectura mantiene latencia en rango status quo Y resuelve la preocupacion del founder de 'sobrecarga del agente'. (3) Si insiste en multi-agente, exigir variante paralelo VERDADERA (Send WhatsApp en branch fire-and-forget via Webhook auto-llamado o Execute Workflow async) y aceptar la race condition documentada con lock SELECT FOR UPDATE en bot-actions — pero esto agrega complejidad que el doc subestima. Antes de cualquier decision: instrumentar latency tracking en el workflow actual (tabla con turn_id + ms por fase) por 1 semana — sin datos reales de baseline, esta discusion es teorica.

### Lens: maintenance [HIGH]

**Findings:**

- **Doble superficie de prompts dinamicos = doble superficie de bugs silenciosos. Hoy hay UN composer (Code node JS) que arma el system prompt desde agency.settings + bot_config. Pasas a DOS composers que tienen que mantenerse coherentes: el del conversador no puede saber de tools, el del analista no puede saber de tono. Si un dia agregas un bloque nuevo (ej. '## DISPONIBILIDAD HORARIA'), tenes que decidir manualmente en cual de los dos va, y a veces va en ambos parcialmente. En 3 meses el founder no va a recordar la regla de particion.**
  - Impacto: Cada cambio de bot_config (cosa que vas a hacer mucho — es el feature core de multi-tenancy) toca 2 archivos en vez de 1, y el riesgo de drift entre prompts crece linealmente con el numero de bloques. Drift = el conversador habla de algo que el analista no entiende, o viceversa. Bug clase 'funciona en dev, falla en agency X'.
- **Debuggear 'el bot no llamo Request_Handoff cuando dijo te paso con humano' se vuelve un problema de correlacion cruzada entre dos traces de LangChain Agent + bot_decisions_log + Postgres memory + logs de bot-actions edge function. Hoy con 1 agente, abris el trace del Agent node en N8N y ves: input, system prompt, tool calls, output. Punto. Con 2 agentes tenes que abrir 2 traces, alinearlos por turn_id, leer el reply del conversador, leer el reasoning del analista, y inferir por que el analista no detecto la senial.**
  - Impacto: MTTR (mean time to resolve) por incidente se multiplica facil 2-3x. Con muchos clientes en produccion, los incidentes que llegan al founder o al soporte son los raros (1 de cada 200 turnos). Esos son justamente los que necesitas debuggear rapido, y son los que mas se complican con el patron multi-agente. La doc dice 'mitigacion: dashboard en CRM admin para inspeccionar turnos' — eso es OTRO sistema que hay que construir y mantener.
- **Agregar una tool nueva (ej. Schedule_Visit_Tool) ahora requiere tocar: (1) bot-actions edge function — igual que hoy, (2) workflow N8N — conectar nueva tool al analista, (3) prompt del analista — agregar descripcion + few-shots + gate de auto_actions, (4) prompt del CONVERSADOR — agregar instruccion 'si el lead pide agendar visita, decile que vas a coordinar' sin que mencione la tool, (5) testear que conversador y analista se entiendan entre si para esa tool nueva. Hoy son 3 pasos: edge function + workflow + prompt unico.**
  - Impacto: El founder dijo 'velocidad de feature' no es la prioridad, pero la friccion para agregar tools afecta la velocidad de iteracion mientras se calibra el bot — que es JUSTO el mes previo a produccion donde mas vas a iterar. Cada tool nueva pasa de '1 hora' a '3-4 horas' por la coordinacion entre 2 prompts.
- **Cantidad de archivos/configs que cambian juntos crece. Hoy un cambio de comportamiento del bot toca: agency.bot_config (DB) + opcionalmente el composer (1 Code node). Con multi-agente: agency.bot_config + composer-conversador (Code node) + composer-analista (Code node) + few-shots del analista (probablemente externalizados a otra tabla porque van a ser muchos) + tabla bot_decisions_log para auditar. La regla del CLAUDE.md 'archivos > 300 lineas dividir en modulos' se va a violar en los Code nodes de N8N (que son nodos individuales monoliticos, no se modularizan bien).**
  - Impacto: En 3 meses cuando el founder vuelva a tocar el bot, la curva de re-onboarding es alta. La skill capturada para esto va a tener que ser muy detallada para que no se pierda el contexto. Y N8N como editor visual NO ayuda a navegar entre Code nodes — todo es click+abrir modal+leer JS, peor que un repo de codigo.
- **Race condition mode-paralelo es un footgun de mantenimiento. La doc lo reconoce ('lead manda mensaje 2 antes de que el analista del turno 1 termine'). La mitigacion propuesta es 'serial estricto o SELECT FOR UPDATE en bot-actions'. SELECT FOR UPDATE en edge functions Deno + Supabase pooler tiene gotchas que NO estan capturados en ninguna skill, y serial estricto mata la ventaja de latencia que justifica el patron. Vas a terminar en serial estricto, y ahi el patron multi-agente se convierte en '1 agente que tarda el doble por nada'.**
  - Impacto: El patron tiene una postura optimista de paralelismo que en mantenimiento se va a degradar a serial por miedo a inconsistencias. Cuando el founder vuelva en 3 meses y vea latencia de 6-8s, no va a recordar por que esta serial y va a 'optimizar' rompiendo la consistencia. Patron facil de regresionar.
- **Dos modelos diferentes (GPT-4 conversador, gpt-4o-mini analista) = dos comportamientos de calibracion separados. Cuando OpenAI deprecate uno, o cuando quieras migrar a Claude/Anthropic, tenes que recalibrar DOS prompts en paralelo, no uno. Hoy migrar de modelo es: cambiar el dropdown del Chat Model, correr 20 conversaciones de test, ajustar prompt. Con 2 agentes: cambiar 2 dropdowns, correr 20 turnos por agente, ajustar 2 prompts manteniendo coherencia entre ambos.**
  - Impacto: Lock-in operativo. Migracion de modelo (que vas a hacer al menos 1-2 veces por ano por economia o por modelo nuevo de Anthropic) pasa de tarea-de-tarde a tarea-de-semana. Para un founder solo, eso es mucho.
- **El 'audit trail nativo' (bot_decisions_log) suena bien en pros pero en mantenimiento es OTRA tabla con su esquema, retencion, indices, y query patterns. No esta en ninguna skill actual. Si se llena (miles de conversaciones/dia * N tools * N turnos = millones de rows/mes) hay que pensar en retention policy, partitioning, etc. Hoy ese log esta implicito en N8N executions + bot-actions logs. No es gratis.**
  - Impacto: Deuda tecnica latente. En 6 meses la tabla pesa GB, las queries del dashboard se ponen lentas, y el founder no va a recordar por que existe. Termina haciendo un DELETE WHERE created_at < ... a las apuradas o pagando storage.

**Recomendacion del juez:** Desde la lens maintenance, esta arquitectura es PEOR que el status quo mejorado (A) y peor que el hibrido determinista (C). El multiplicador 2x en superficie cognitiva (2 prompts, 2 traces, 2 modelos, 2 ciclos de calibracion, 1 tabla extra de auditoria) NO se compensa con beneficios proporcionales en debuggeabilidad. La opcion C (1 agente conversa + Information Extractor JSON + nodos N8N condicionales) tiene mejor perfil de mantenimiento porque sustituye un agente caja-negra por un schema explicito + condicionales visibles en el canvas N8N — eso SI se puede entender en 3 meses sin re-leer skills. Si el dolor real es 'el agente no llama tools que deberia' (queja #4 del founder), la causa raiz mas probable es prompt-saturation, no necesidad de otro agente: dividir el prompt en bloques mejor estructurados + agregar few-shots de tool-calling al prompt actual + Information Extractor para datos estructurados resuelve el 80% del problema con 1/3 de la complejidad. Recomendacion: NO ir a la arquitectura B. Probar A+C en paralelo durante el mes de calibracion. Reservar B solo si A+C no logra el target de tool-call accuracy.

## Hibrido determinista (Information Extractor + nodos N8N)

### Lens: reliability [HIGH] BLOCKER

**Findings:**

- **Doble LLM call en serie multiplica la tasa de fallo por turno. Si OpenAI tiene 99.5% disponibilidad (real, no marketing), un solo call = 0.5% fail. Dos calls independientes en el mismo turno = ~1% fail rate. Con miles de conversaciones simultaneas en pico, son DECENAS de turnos por hora donde el extractor falla silenciosamente. La rama de reply funciona, el lead recibe respuesta, pero la accion NUNCA se ejecuta. Peor: nadie se entera salvo que alguien lea logs.bot_action_failures.**
  - Impacto: Datos perdidos invisibles. Lead dice 'mi presupuesto son $200k' -> Sofia responde 'perfecto, anotado' -> extractor falla -> budget NUNCA se guarda. El agente humano despues mira el CRM y no ve el dato. Erosion de confianza con clientes pagantes.
- **El reply se manda ANTES de validar que el extractor funcione, y Sofia (sin tools) puede prometer acciones que no van a ocurrir. Ejemplo: lead dice 'quiero hablar con alguien' -> Sofia responde 'te conecto con un agente ahora' -> extractor falla / no extrae handoff_reason / confidence < 0.8 -> handler sigue siendo 'bot' -> Telegram nunca dispara -> lead queda atrapado conversando con bot creyendo que viene un humano. Esto es PEOR que el status quo, donde tool-calling y reply estaban acoplados semanticamente.**
  - Impacto: Promesas rotas al lead. En real estate donde el lead esta caliente y el tiempo importa, esto mata deals. El founder pierde clientes pagantes cuando agencias detectan que el bot 'miente'.
- **La rama paralela NO tiene garantia de orden ni de atomicidad multi-turno. Turno N escribe extractor_json al edge function, turno N+1 llega antes de que se complete el INSERT del turno N (porque YCloud no espera al extractor para reenviar). Sofia turno N+1 lee lead.attributes_actuales STALE desde memory composer (paso 3) y el extractor turno N+1 cree que el dato no existe -> intenta extraerlo de nuevo -> escribe duplicado / sobreescribe / dispara update redundante.**
  - Impacto: Race condition real en conversaciones rapidas (lead que manda 3 mensajes seguidos en 5s, comun en WhatsApp). Stage cambia y vuelve. Tags se duplican. Handoff se dispara dos veces (dos alertas Telegram al agente humano por el mismo lead). Imposible de reproducir en testing manual, aparece en pico.
- **El Code node de 'Componer Schema Dinamico' (paso 7) es un SPOF multi-tenant. Si un dev cambia agency.settings.pipeline_stages a un valor que rompe el JSON schema (ej. nombre con caracteres invalidos para enum, o array vacio), el Information Extractor de N8N tira error de validacion y TODA la agencia se queda sin extractor. Peor: el reply ya se mando (paso 6), entonces el lead sigue conversando pero ninguna accion se escribe a DB. Silent degradation.**
  - Impacto: Una agencia mala configurada puede romper ESA agencia entera sin que ninguna alerta clara salte. El founder se entera por ticket de soporte del cliente cuando este nota que 'el bot no esta capturando leads'.
- **Information Extractor en N8N (basado en function calling de LangChain) tiene tasa de fallo NO-cero en JSON parsing cuando el modelo es gpt-4o-mini y el contexto crece. Especificamente: schemas con muchos campos opcionales + enums dinamicos por agencia + ultimo mensaje del lead en espanol con jerga regional (CR/MX/AR variaciones) -> gpt-4o-mini ocasionalmente devuelve JSON con campos no-declarados, valores fuera del enum, o truncado. El node de N8N falla y la rama entera se pierde.**
  - Impacto: Tasa de fallo asimetrica por agencia: agencias con pipeline complejo (10+ etapas, 20+ tags) van a tener mas errores que agencias simples. El founder no va a saber esto hasta que un cliente premium se queje. Falta un retry con prompt mas restrictivo o fallback a gpt-4o.
- **Cero estrategia explicita de retry / dead letter queue. El brief dice 'Error Trigger -> log a logs.bot_action_failures -> sigue'. Esto NO es resiliencia, es resignacion. Si el edge function bot-actions tiene un blip de 503 (Supabase reinicia, cold start de edge function, network flap), la accion se pierde permanentemente. En el status quo el agente puede en el siguiente turno re-evaluar y volver a llamar la tool; en C el JSON ya fue 'consumido' y no se reintenta.**
  - Impacto: Bajo carga real (cientos de conversaciones simultaneas), las 503/timeouts de Supabase Edge ocurren. Sin retry con backoff + DLQ procesable, perdes 0.5%-2% de acciones de DB silenciosamente. En 10k turnos/dia son 50-200 acciones perdidas/dia. Inaceptable para multi-tenant pagante.
- **Postgres Memory en LangChain Agent + escritura asincrona desacoplada = lectura incoherente entre turnos. La memoria de Sofia se actualiza al final del turno con el reply, pero las attributes del lead se actualizan en rama paralela DESPUES. En el turno N+1, system prompt composer (paso 4) lee lead.attributes_actuales que puede estar atras de lo que la memoria conversacional refleja. Sofia 'recuerda' que el lead dijo su nombre pero el bloque ## DATOS YA CAPTURADOS no lo muestra -> Sofia pregunta el nombre OTRA VEZ.**
  - Impacto: UX rota visible al lead. 'Ya te dije mi nombre' es el #1 complaint de bots de WhatsApp. El sistema parece roto incluso cuando tecnicamente funciono.
- **No hay circuit breaker entre Sofia y el extractor. Si OpenAI esta degradado (latencia >10s), Sofia con gpt-4o-mini puede recuperarse rapido para responder al lead, pero el extractor con gpt-4o-mini en paralelo se cuelga -> N8N execution se mantiene abierta -> bajo carga real esto agota workers del N8N self-hosted en Easypanel. N8N tiene cap de ejecuciones concurrentes, y workflows colgados consumen ese cap.**
  - Impacto: Cascada: latencia OpenAI -> N8N saturado -> nuevos webhooks de YCloud encolan -> latencia visible al lead se dispara aunque el reply en si sea rapido. Sin timeout agresivo en el node del extractor + circuit breaker, una degradacion externa tumba el sistema.
- **El campo 'confidence' propuesto como mitigacion de hallucinations es un parche que no resuelve el problema. gpt-4o-mini no calibra bien su confidence; pedirle a un LLM su propio confidence es notoriamente poco confiable. Filtrar por confidence >= 0.8 va a generar tanto falsos negativos (datos validos descartados) como falsos positivos (hallucinations con high confidence). Esto NO es una mitigacion seria, es teatro de seguridad.**
  - Impacto: Falsa sensacion de robustez. El founder va a creer que esta protegido cuando en realidad sigue siendo vulnerable a extracciones fantasma. Necesita validacion deterministica (regex sobre el mensaje literal, comparacion contra valores del enum agency-scoped) NO confidence del LLM.
- **Falta plan de observabilidad y alerting. 'Audit Log al final' es necesario pero no suficiente. No hay metrica de tasa-de-fallo-del-extractor por agencia, ni alertas si esa tasa sube >X%. No hay tracing distribuido entre el reply branch y el actions branch para correlacionar fallos. Con cientos de agencias en multi-tenant, sin esto vas a ciegas.**
  - Impacto: Tiempo de deteccion de problemas en produccion = tiempo que tarda un cliente en quejarse. Para un sistema que el founder quiere llevar a 'muchos clientes', esto es inaceptable. Necesita Sentry + dashboard de tasa-de-extractor-fail por agencia ANTES de produccion.

**Recomendacion del juez:** NO ir a produccion con esta arquitectura tal como esta brifeada sin agregar 5 mitigaciones obligatorias: (1) Reply de Sofia DEBE ser conservador y NO prometer acciones que dependen del extractor — cambiar prompt para que diga 'voy a registrar eso' en vez de 'ya te lo asigne'; idealmente esperar al extractor para confirmar antes de prometer handoff. (2) Implementar retry exponencial + DLQ procesable (tabla bot_action_dead_letter con worker que reintenta cada 5min con backoff) para los HTTP Request al edge function. (3) Re-leer lead.attributes_actuales DENTRO del Code node que arma el schema dinamico (paso 7) en lugar de usar el snapshot del paso 3, para reducir race conditions multi-turno. Idealmente un advisory lock en Postgres por lead_id durante el turno. (4) Reemplazar el campo 'confidence' por validacion deterministica: regex/parsing del mensaje literal para campos como budget/email/phone, y match estricto contra enums agency-scoped para stage/tags. (5) Timeout agresivo (5s) + circuit breaker en el node del extractor; si OpenAI esta degradado, abrir el circuito y dejar el extractor en bypass por X minutos para no saturar N8N. Ademas: tests unitarios obligatorios sobre el Code node del schema dinamico con fixtures de 5+ agency.settings reales, y dashboard de tasa-de-extractor-fail por agencia con alerta si pasa 2%. Mientras estos 5 puntos no esten implementados, el sistema NO esta listo para 'muchos clientes pagantes'.

### Lens: cost [LOW]

**Findings:**

- **El claim de '0.4x del status quo' es matematicamente correcto pero engana la magnitud real. Status quo con GPT-4 a ~3000 tokens input + ~150 output = ~$0.04/turno. Arquitectura C: Sofia gpt-4o-mini (1800 in + 150 out) = ~$0.00036 + Extractor gpt-4o-mini (~2200 in con prompt+turno+attrs + ~100 out json) = ~$0.00039. Total ~$0.00075/turno. Eso NO es 0.4x — es ~0.019x (50x mas barato). El brief subestima el ahorro real por casi 25x. No es un problema, es buena noticia, pero indica que los numeros del brief estan mal calibrados.**
  - Impacto: Decision-making con datos imprecisos. Si el founder presupuesta basado en '0.4x' (~$0.016/turno) vs la realidad (~$0.0008/turno), va a sobre-aprovisionar. No bloquea produccion pero hay que recalcular el unit economics antes de pricing al cliente.
- **El ahorro depende criticamente de bajar Sofia a gpt-4o-mini. Si por calidad conversacional hay que mantener gpt-4o (no mini) en Sofia: input 1800 tokens * $2.50/1M + output 150 * $10/1M = ~$0.006/turno + extractor mini $0.0004 = ~$0.0064/turno. Eso es 0.16x del status quo (6x mas barato) — todavia bueno, pero el caso '25x mas barato' del brief asume mini para conversar Y mini para extraer. Si el founder testea mini conversando y resulta robotico/poco empatico para inmobiliaria (donde el tono importa), el ROI se reduce a 6x — sigue siendo positivo pero no la bala de plata.**
  - Impacto: Riesgo de regresion de calidad conversacional al bajar de GPT-4 a 4o-mini. Esto NO es problema de costo en si — es que el ahorro prometido es contingente a una decision de modelo que aun no se valido. Mitigable con A/B test de 50 conversaciones reales antes de commit.
- **Costo del extractor escala 1:1 con turnos, no con acciones. En conversaciones largas donde el lead solo charla (sin datos nuevos), el extractor corre igual y paga tokens igual aunque el JSON salga vacio. Status quo: si el agente decide no llamar tools, no hay segundo call. Arquitectura C: segundo LLM call SIEMPRE, incluso en turnos sin nada que extraer. En conversaciones tipicas inmobiliarias de 15-25 turnos donde 60% son small talk/preguntas del lead, eso es 9-15 calls de extractor 'desperdiciados' por conversacion. A escala de miles de conv simultaneas en pico, eso son ~$3-5 extras/dia por agencia activa — irrelevante en absoluto, pero arquitecturalmente es waste.**
  - Impacto: Optimizacion futura clara: gate del extractor con un Code node previo que detecta heuristicamente si vale la pena correrlo (mensaje del lead contiene numero, email pattern, palabras clave de stage como 'visita/agendar'). Reduce calls del extractor 40-60% sin perder precision. No bloquea produccion, es post-MVP.
- **Escalabilidad a miles de conv simultaneas: el bottleneck NO es costo de tokens (negligible) sino rate limits de OpenAI. Tier 4 de OpenAI da 10000 RPM combinado para gpt-4o-mini. Con C, cada turno = 2 requests. En pico de 5000 turnos/min = 10000 requests/min = exactamente el limite del tier 4. Status quo con 1 sola llamada GPT-4 hace 1 request por turno pero el limite de GPT-4 es mas estricto (~500 RPM en tier 3). En la practica, mini tiene mucho mas headroom, pero el founder tiene que verificar su tier de OpenAI antes de prometer 'miles de conv simultaneas'.**
  - Impacto: No es bloqueo de produccion pero es una verificacion pendiente. Solucion trivial: subir a tier mas alto de OpenAI (automatico con uso) o agregar fallback a Azure OpenAI. Hay que medirlo, no asumirlo.
- **Costo de auditoria/storage no contabilizado. El paso 12 (Audit Log) escribe el JSON del extractor a Postgres en CADA turno. Con miles de conv simultaneas y promedio 20 turnos/conv = ~20000 INSERTs/dia por agencia. JSON del extractor + metadata pesa ~2-5KB por row. 100 agencias activas = ~10-50GB/mes de logs. Supabase cobra storage progresivamente. No es caro pero hay que prever retention policy (ej. truncar a 90 dias) o el costo de Supabase crece linealmente con uso.**
  - Impacto: Item operacional, no bloqueante. Definir retention en el momento de armar el schema de la tabla audit_log evita refactor a los 6 meses.

**Recomendacion del juez:** Desde la lente costo, la arquitectura C es estrictamente mejor que el status quo y NO es blocker — al contrario, es el principal pro de la propuesta. Acciones concretas: (1) recalcular los numeros del brief con precios reales de OpenAI 2026 — el ahorro real es ~50x no 25x si todo va a mini, ~6x si Sofia queda en 4o full; (2) hacer A/B test de calidad conversacional Sofia gpt-4o-mini vs gpt-4o full ANTES de comprometer el modelo (50 conv reales del golden set); (3) verificar tier actual de OpenAI y proyectar RPM en pico esperado — el costo de tokens es trivial pero el rate limit puede ser real con miles de conv; (4) definir retention policy de audit_log desde el dia 1 (90 dias parece razonable, archivar a S3 lo viejo); (5) planificar como optimizacion v2 el gate heuristico previo al extractor para skipear turnos de small talk — no es necesario para MVP pero es la siguiente mejora obvia. Conclusion: el costo no es problema, es la mejor parte de la propuesta. Los riesgos viven en otras lentes (cobertura de schema, latencia de acciones, multi-tenant complexity).

### Lens: latency [MED]

**Findings:**

- **El claim 'lead ve respuesta en ~2s' es marketing, no medicion. El camino critico hasta el WhatsApp del lead es: YCloud webhook (~100-300ms cold) -> Resolve Agency Postgres (~50-150ms) -> Resolve Lead+Conversation Postgres (~80-200ms, 2 queries) -> Code node Componer Prompt (~20-50ms) -> LangChain Agent gpt-4o-mini + carga de Postgres Memory (~1.2-2.5s, depende del largo del historial) -> HTTP Request a YCloud send (~200-600ms con TLS handshake + API de Meta detras). Suma realista: 1.6s en p50, 3.5-4s en p95. NO 2s como dice el brief. El brief compara con un status quo de 3-6s que ya esta inflado por GPT-4 + 7 tool definitions cargadas en cada call.**
  - Impacto: Expectativa mal calibrada — si el founder vende 'respuesta en 2s' internamente y mide produccion ve 3-4s, va a creer que algo se rompio cuando es el baseline real. Igual sigue debajo del umbral de 8-10s, asi que no es blocker.
- **Postgres Memory de LangChain en N8N hace SELECT del historial completo de la conversacion en cada turno. En conversaciones largas (lead que vuelve 3 dias despues con 40 mensajes acumulados), ese SELECT + serializacion + envio a OpenAI como context se vuelve el bottleneck oculto. A los 50+ turnos puede agregar 500-1500ms solo en la query + 1-2s extra en el LLM por mas tokens de input. El brief no menciona estrategia de window/truncate de memoria.**
  - Impacto: Latencia degrada con la antiguedad de la conversacion. En multi-tenant con cientos de leads activos, los leads viejos cargan mas que los nuevos — comportamiento contra-intuitivo y dificil de debuggear en produccion.
- **El Information Extractor corre 'en paralelo' segun el brief, pero N8N no es realmente paralelo dentro de un mismo workflow — los branches se ejecutan en el event loop de Node pero comparten el mismo worker. Si el extractor toma 1.5s y hay 200 conversaciones simultaneas en pico, el worker se satura y la latencia del PROXIMO mensaje (de otro lead) sube. La 'rama paralela' solo es paralela dentro de UN turno; entre turnos de distintos leads es cola FIFO segun configuracion de N8N (concurrency workers). El brief no analiza throughput, solo latencia de un turno aislado.**
  - Impacto: A escala objetivo (cientos-miles simultaneas), el cuello de botella no es la latencia del LLM sino la concurrency de N8N self-hosted en Easypanel. Necesita configurar EXECUTIONS_PROCESS=main + N8N_CONCURRENCY_PRODUCTION_LIMIT + worker mode con Redis queue, o se va a apilar. Esto no es propio de la arquitectura C — pasa con cualquiera de las 4 opciones — pero el brief lo vende como 'mejor latencia' sin reconocer que el cuello esta en otra parte.
- **El Code node 'Componer Schema Dinamico' (paso 7) se ejecuta CADA turno por cada lead. Si agency.settings tiene 8 etapas + 30 tags permitidos + 12 datos a capturar, armar el JSON Schema runtime + validar + pasarlo al Information Extractor agrega ~30-100ms de CPU node + tokens extras en el prompt del extractor (los enums inflan input). No es catastrofico pero el brief lo presenta como gratis. A escala: 1000 turnos/min * 50ms = 50s de CPU/min solo en armar schemas — un worker de N8N entero.**
  - Impacto: Costo de CPU oculto. Mitigable con cache por agency_id (TTL 5min), pero el brief no lo menciona como requirement de implementacion — y sin cache, el Code node se vuelve un hot path.
- **El audit log (paso 12) es un INSERT a Postgres que el brief pone 'al final del flujo'. Si esta despues del Merge pero antes de cerrar la ejecucion del workflow, agrega ~50-150ms al wall-clock total. No afecta lo que SIENTE el lead (el reply ya salio) pero si la ejecucion del workflow no cierra hasta que el audit log commitea, retrasa la liberacion del worker y reduce throughput.**
  - Impacto: Throughput-killer marginal. Facil de mitigar con fire-and-forget (INSERT en una rama desconectada del flujo critico) pero el brief no especifica eso.
- **El brief dice que las acciones en DB se completan '~1.5s despues del reply'. Eso es OK para extract/tag/note (silenciosos), pero para HANDOFF es problematico: si el lead pide hablar con humano, el reply de Sofia se manda primero ('claro, te conecto con alguien'), y 1.5s despues recien se dispara la alerta a Telegram y se cambia handler='human'. En esa ventana de 1.5s, si el lead manda otro mensaje, el bot lo sigue contestando porque handler todavia es 'bot'. Bug sutil pero real en multi-tenant.**
  - Impacto: Handoff con race condition de ~1-2s. En la mayoria de casos no se nota; en agencias con leads ansiosos que mandan 3 mensajes seguidos cuando piden humano, el bot puede responder uno o dos mensajes que NO deberia. Mitigable forzando que handoff sea sincrono (esperar al extractor antes de mandar reply si hay senales de frustracion), pero eso anula la ventaja de latencia de paralelizar.

**Recomendacion del juez:** La lente de latencia NO bloquea produccion. El camino critico hasta el WhatsApp del lead es 1.6s p50 / 3.5-4s p95 realista — comodamente debajo del umbral de 8-10s, y materialmente mejor que el status quo con GPT-4 + 7 tools (4-6s p50). Pero antes de declarar victoria, exigir tres cosas: (1) decidir estrategia de window de Postgres Memory (truncar a ultimos N turnos o resumir cada K) para que conversaciones largas no degraden; (2) cachear el output del Code node de schema dinamico por agency_id con TTL para no recomputar cada turno; (3) hacer el audit log y el handoff con cuidado — audit fire-and-forget, handoff sincrono cuando se detectan senales de frustracion fuertes en el extractor (aceptar +1s en ese caso especifico vs race condition con bot respondiendo en paralelo). El bottleneck real a escala objetivo no es la latencia del LLM en un turno, es el throughput de N8N self-hosted en Easypanel — configurar worker mode con Redis queue + concurrency limit ANTES de tener clientes reales, sino se cae con 100 conversaciones simultaneas independientemente de que arquitectura elijan.

### Lens: maintenance [HIGH]

**Findings:**

- **Agregar una accion nueva (ej. tipo_propiedad, assigned_user) requiere editar 3-4 lugares en N8N + 1 en edge function, vs 1 tool nueva en status quo. Hoy son: (a) Code node 'Componer Schema Dinamico' agregando campo al JSON schema, (b) prompt del Information Extractor explicando cuando llenarlo, (c) nuevo IF/Switch con regla de idempotencia, (d) nuevo HTTP Request al endpoint correspondiente, (e) si la accion es nueva en bot-actions, agregar la rama en el edge function. Cinco archivos cambian juntos para una sola feature. En produccion con muchos clientes, donde el founder va a pedir 'capturar X campo nuevo' cada 2 semanas, esto se vuelve fricciona constante.**
  - Impacto: Velocidad de iteracion cae 2-3x los primeros 6 meses cuando el dominio aun esta cambiando. El founder ya marco 'riesgo real en velocidad de iteracion los primeros 2 meses' en su propio brief — esto subestima el horizonte real.
- **El Code node 'Componer Schema Dinamico' es un single point of failure invisible para multi-tenant. Si tiene un bug (ej. enum mal serializado, escape de comillas en tag con caracter especial, agency.settings con shape inesperado de una agencia migrada), TODAS las agencias se rompen al mismo tiempo en el siguiente turno. Y el bug no aparece en logs de OpenAI ni en la conversacion — el extractor simplemente devuelve {} o un JSON malformado. La unica forma de detectarlo es revisar el audit log post-hoc.**
  - Impacto: Cuando algo se rompe a las 11pm del sabado con 50 agencias en produccion, el primer reflejo del founder va a ser 'mirar el chat con Sofia' — y no va a ver nada raro ahi porque Sofia respondio bien. El bug vive en un Code node que solo se ve abriendo la ejecucion de N8N especifica. Tiempo medio de diagnostico: 30-60min vs 5min en status quo donde el agente o llama la tool o no la llama (visible en tool_calls del log de OpenAI).
- **Doble fuente de verdad sobre el estado del lead: Sofia conversa con memoria conversacional (Postgres), el extractor analiza el turno aislado con lead.attributes_actuales como contexto. Cuando divergen (ej. Sofia ya pidio el telefono y lo tiene en memoria, pero el extractor lo re-extrae del mensaje y dispara update redundante; o Sofia infiere stage_change de tono general, extractor no lo ve), debuggear cual de los dos esta mal requiere comparar (a) Postgres memory rows, (b) input al extractor, (c) output del extractor, (d) lead.attributes en DB pre-turno, (e) lead.attributes post-turno. Cinco fuentes de datos para reconstruir UN turno.**
  - Impacto: El founder volviendo en 3 meses va a tener que aprender a leer 5 lugares distintos para entender por que un lead quedo en estado raro. En status quo son 2 (memoria + tool_calls del log). Esto se siente peor si el bug es intermitente (1 de cada 20 turnos).
- **Audit log es el activo de debugging pero su esquema no esta definido en el brief. Cuando el extractor falle silencioso (devuelve {} pero el lead claramente dijo 'me llamo Juan'), necesitas guardar TAMBIEN el prompt del extractor + el input crudo + el modelo usado + version del schema dinamico. Si solo se guarda extractor_output_json + actions_disparadas (como dice el brief), no se puede reproducir el fallo offline. Y como el schema cambia por agencia y por settings, hay que versionar el schema usado en cada ejecucion.**
  - Impacto: El 'debugging trivial' que vende esta arquitectura solo es real si el audit log captura suficiente contexto para reproducir. Tal como esta especificado, captura el 'que' pero no el 'por que' — y el por que es donde vive el bug.
- **Cognitive load del founder al volver en 3 meses: hoy 'agente con 7 tools' es un mental model dominante en la industria (cualquier dev con experiencia LangChain lo entiende en 10min). El hibrido determinista es un patron menos comun que mezcla 2 LLM calls, ramas paralelas en N8N, un schema dinamico construido en runtime, 6 IF/Switch idempotentes, y un audit log. No hay un nombre comun para esto. La curva de re-aprendizaje cuando el founder (o un futuro dev) lo retome es alta.**
  - Impacto: Onboarding de un dev nuevo: 1-2 dias para entender vs 2-4 horas con status quo. Para un equipo de 1 persona que rota contexto entre proyectos, esto se nota. Tambien afecta al founder cuando vuelva a tocar el bot tras 3 meses de trabajar en otra cosa (admin panel, outbound).
- **Acoplamiento entre Sofia (conversador) y extractor via prompts independientes: Sofia promete 'te asigno con Pedro' pero el extractor no tiene 'assigned_user' en el schema o no detecta el patron 'asignar' en lenguaje natural. La conversacion se desincroniza de la accion. En status quo el agente que dice 'te asigno con Pedro' es el mismo que llama Assign_Tool — coherencia garantizada por construccion. En el hibrido la coherencia depende de mantener 2 prompts en sync, en 2 nodos distintos del workflow.**
  - Impacto: Cada vez que el founder cambie el tono o el comportamiento de Sofia (ej. 'que sea mas proactiva ofreciendo agendar visita'), tiene que recordar tambien tocar el prompt del extractor para que detecte esos casos. Esa coordinacion mental es exactamente el tipo de cosa que se olvida en mes 4 y aparece como bug intermitente en mes 6.
- **Tests automatizados son posibles pero no triviales: el founder dice 'testeable con fixtures sin LLM' refiriendose a las ramas IF/Switch, pero el extractor ES un LLM y es el que mas falla. Para testear el extractor con calidad real necesitas un golden set (el founder lo menciona — conversaciones grabadas), un harness que ejecute el extractor contra cada turno, y assertions sobre el JSON esperado. Eso no existe hoy y no esta en los '2-3 dias de implementacion'. Sin ese test suite, no hay forma de saber si un cambio al prompt del extractor regresiona casos.**
  - Impacto: En el papel el sistema es testeable; en la practica nadie va a montar ese harness en mes 1. Resultado: cada cambio al prompt del extractor o al schema se valida 'a ojo' contra 3-4 casos en chat, y los bugs aparecen en produccion con clientes reales 2 semanas despues.

**Recomendacion del juez:** No es blocker para produccion, pero la lens maintenance revela que el costo principal de esta arquitectura no es latencia ni $ — es velocidad de iteracion + capacidad de debuggear bajo presion. Antes de migrar a este patron como produccion-multi-tenant: (1) Definir el audit log con TODO el contexto reproducible (extractor_prompt_used + schema_version + input_crudo + modelo + tokens + latencia por nodo), no solo el JSON de salida; (2) Crear un harness de tests sobre el extractor con golden set de >=30 turnos reales por agencia tipo antes de cortar trafico real — sin esto el 'debugging trivial' es marketing; (3) Documentar EL PATRON como skill 'agregar accion al hibrido determinista' con checklist de los 5 archivos que cambian juntos, ANTES de la primera vez que el founder lo necesite (no despues); (4) Versionar el schema dinamico (hash de agency.settings que lo produjo) en cada fila del audit log para poder reproducir el contexto exacto de un turno cuando algo falla; (5) Considerar mantener UNA tool en Sofia: 'request_clarification' o equivalente — un escape hatch para casos que el extractor no captura, asi no se pierde la capacidad conversacional rica del status quo cuando aparece un caso fuera de schema; (6) Plan explicito de quien y cuando va a revisar el audit log — sin un proceso (ej. dashboard de 'turnos con extractor_output={}'), el log se acumula sin valor.

## Pipeline secuencial con LLM auditor mas chico

### Lens: reliability [HIGH] BLOCKER

**Findings:**

- **Fire-and-forget del send WhatsApp ANTES del auditor crea un estado inconsistente irrecuperable cuando el auditor falla. Si el bot dice 'te asigno con Juan, ya te contacta' (nodo 7 ejecuta) y luego el auditor (nodo 10) falla por timeout/JSON invalido/429 de OpenAI, el lead recibe una promesa que nunca se cumple. NO HAY rollback posible — no podes 'des-enviar' el mensaje de WhatsApp. El lead queda esperando a Juan que nunca aparece. A escala de miles de conversaciones esto se vuelve un problema de NPS/reputacion sistemico, no un edge case.**
  - Impacto: Promesas incumplidas al lead son peores que latencia. El sistema queda con discrepancia permanente entre 'lo dicho' y 'lo hecho' sin mecanismo de reconciliacion. En real estate esto = lead perdido + agente furioso con la agencia.
- **Request_Handoff con auditor pequeno es la mayor pieza critica de negocio Y es donde gpt-4o-mini es estructuralmente debil. Detectar handoff requiere comprension de intencion sutil ('no me esta convenciendo este bot', 'quiero hablar con alguien que sepa', 'mi caso es complicado', sarcasmo, frustracion acumulada de turnos previos). gpt-4o-mini con prompt corto + few-shots NO captura esto consistentemente. Falso negativo en handoff = lead caliente atrapado con el bot = agencia pierde la venta. El documento mismo lo admite ('Mitigacion: regex sobre quiero hablar con humano|agente real|persona') — pero regex no captura el 80% de los casos reales de frustracion.**
  - Impacto: La tool mas critica del negocio (la unica que decide cuando entregar el lead al humano) corre en el modelo mas barato. Inversion de prioridad de fiabilidad.
- **Sin idempotencia en bot-actions el sistema rompe ante el retry obvio. Si el HTTP a bot-actions del nodo 13 falla con timeout pero la edge function YA escribio en DB (caso clasico de timeout post-write), un retry duplica Tags, Notes, Assigns. Para Qualify y Stage el lead salta dos veces. No veo nada de idempotency_key (turn_id+tool+params hash) ni en el flujo ni en bot-actions. A miles de conversaciones/dia con N8N self-hosted en Easypanel (que sufre reinicios y network blips) esto pasa, no 'puede pasar'.**
  - Impacto: Datos corruptos en multi-tenant (lead reasignado dos veces, etiquetas duplicadas, notas duplicadas en lead_notes). Soporte se va a inundar de tickets de agencias diciendo 'el bot puse a Juan asignado tres veces'.
- **Split Out + Switch + 7 HTTP Requests paralelas sin coordinacion de orden ni transaccionalidad. Si el auditor devuelve [Extractor, Stage, Qualify] en un turno, ejecutarlas en paralelo es WRONG: Qualify depende de que Extractor haya escrito attributes primero (sino califica sobre estado viejo); Stage depende de Qualify (puede haber regla 'no mover a Calificado sin razon'). En N8N las branches paralelas del Switch no garantizan orden de completion. A escala vas a tener race conditions intermitentes que solo se ven con volumen.**
  - Impacto: Estado del lead inconsistente segun el orden de completion de los HTTP. Bugs no-deterministicos imposibles de reproducir en dev — el peor tipo de bug en produccion multi-tenant.
- **Memory de LangChain (Postgres chat memory) solo la actualiza el conversador, NO el auditor. Si en el turno N el auditor decide 'el lead dio su nombre Juan, ejecutar Extractor', en el turno N+1 el conversador NO sabe que ya capturo 'Juan' en attributes (a menos que se vuelva a leer attributes del lead en cada turno, lo cual el flujo no muestra explicitamente que haga). Esto causa: el bot vuelve a preguntar 'como te llamas' aunque ya lo capturo. Romp e la confianza del lead en la primera conversacion de demo.**
  - Impacto: Bot que repite preguntas = lead piensa 'este bot es tonto' = handoff temprano forzado o lead pierde interes. Es exactamente el problema que el founder ya conoce de bots de inmobiliaria mediocres.
- **Dead-letter queue propuesta como 'mitigacion' del fallo del auditor es vaporware en el documento. No esta especificado: (a) quien lee bot_audit_failures, (b) cada cuanto, (c) que politica de retry (la decision del auditor puede ser irrelevante 5 min despues — el lead ya siguio la conversacion y el estado cambio), (d) si re-ejecutar acciones viejas sobre estado nuevo corrompe datos. Un retry de un Stage_Tool 10 minutos despues, cuando el lead ya esta en otra etapa, es PEOR que no retry.**
  - Impacto: La 'red de seguridad' del sistema no existe operativamente. En produccion los fallos del auditor se van a acumular silenciosamente en una tabla que nadie monitorea.
- **Latencia agregada de OpenAI bajo carga real esta subestimada. p95 de GPT-4 chat completions sube a 8-15s bajo load (rate limits compartidos por org, retries internos del SDK). Sumado a gpt-4o-mini en p95 (~3-5s, no 1-2s como dice el doc), end-to-end realista es 15-25s en mal momento. Pero MAS CRITICO: la auditoria corre DESPUES del send, asi que cuando el auditor tarda mucho y el lead manda OTRO mensaje en ese tiempo, te entras en condicion de carrera: el conversador del turno N+1 arranca antes de que el auditor del turno N termine, el estado del lead todavia no se actualizo, el conversador opera sobre datos viejos.**
  - Impacto: Race condition entre auditor de turno N y conversador de turno N+1 en conversaciones rapidas (las que mas importan: leads calientes que tipean rapido). Estado divergente sistematico.
- **El YCloud webhook no tiene mencionada idempotencia/dedup en el flujo. YCloud reintenta webhooks ante 5xx o timeout (>20s habitualmente). Si N8N se demora por carga (workflow corriendo lento, openai lento), YCloud reintenta el mismo message_id, el flujo corre dos veces, el bot responde dos veces al lead. A escala de miles de conversaciones en pico esto es garantizado.**
  - Impacto: Mensaje duplicado al lead via WhatsApp + doble ejecucion de auditor + doble escritura de tools. Es el bug clasico de webhooks sin dedup y va a pasar el primer dia de carga real.
- **Multi-tenancy: bot_config se lee en el nodo 2 (Resolve Agency) y se inyecta al prompt del auditor en nodo 9. Si la agencia cambia su config (auto_actions toggles, tools permitidas) durante una conversacion en curso, el conversador puede prometer algo (basado en config vieja del prompt) y el auditor (con config nueva si se re-resuelve) decide no ejecutar. Misma desincronizacion que el doc menciona, pero amplificada por ser cross-tenant: una agencia editando settings impacta conversaciones de OTRA agencia si hay caching mal hecho.**
  - Impacto: Si hay cualquier capa de cache (lo cual a escala vas a necesitar para no martillear Supabase), la invalidacion cross-tenant es no trivial y propensa a leaks.
- **Information Extractor de N8N con schema estricto en gpt-4o-mini falla mas seguido de lo que el doc admite. gpt-4o-mini sigue schema bien ~95% de las veces, pero ese 5% en miles de turnos diarios son decenas de fallos al dia. La 'mitigacion' propuesta (additionalProperties: true + validacion post-hoc) basicamente desactiva la garantia del schema. Quedas en lo mismo que GPT-4 sin tools: validacion manual frangil.**
  - Impacto: El argumento 'pro' de validacion automatica del Information Extractor se diluye en la practica. No es la red de seguridad que el doc vende.

**Recomendacion del juez:** NO ir a produccion con esta arquitectura tal cual. Antes de considerarla viable hay que cerrar 4 cosas no negociables: (1) Idempotency keys end-to-end: YCloud message_id como dedup en webhook, turn_id+tool+params_hash como idempotency en bot-actions (la edge function debe rechazar duplicados). (2) Send WhatsApp DESPUES del auditor para acciones criticas, o hacer el conversador "tools-aware" en el texto: prohibirle prometer acciones especificas ('te asigno con Juan') a menos que la accion ya este ejecutada — el bot debe hablar en condicional hasta que el auditor confirme. (3) Request_Handoff NO puede correr en gpt-4o-mini puro. Debe tener doble red: (a) rule-based detector ANTES del auditor (regex + clasificador chico entrenado sobre frustration markers reales del dominio), (b) auditor mini como fallback. Costo extra es despreciable y la criticidad lo justifica. (4) Ejecutar las acciones secuencialmente y en orden semantico (Extractor -> Qualify -> Stage -> Tag -> Assign -> Note -> Handoff), no en paralelo. Performance no es el cuello de botella aca. Si se cierran esos 4, la arquitectura es razonable pero NO la mejor opcion: la opcion C (hibrido determinista con Information Extractor de campos estructurados + reglas N8N para acciones obvias como Extractor/Tag/Note + auditor LLM solo para decisiones interpretativas como Qualify/Handoff) tiene menor blast radius y es mas observable. Recomiendo: primer mes en produccion con opcion C como camino real, opcion D queda para iteracion 2 si C no alcanza la flexibilidad necesaria.

### Lens: cost [HIGH]

**Findings:**

La arquitectura promete '+0ms percibida' pero ese +0 es relativo al status quo malo, no a un sistema rapido. Si hoy el founder ya se queja de latencia (3-6s con tools), esta arquitectura no la baja — solo evita empeorarla.**
  - Impacto: El founder esperaba que separar responsabilidades hiciera al conversador mas rapido (~2-4s sin tools). En la practica GPT-4 sin tools sigue siendo 2.5-5s en p50 y 6-8s en p95 por la red OpenAI + tokens de respuesta. La ganancia real es ~500-1500ms, no la mitad. No es un cambio de categoria de UX.
- **Latencia OPERATIVA del workflow N8N se duplica en numero de nodos criticos del path. Status quo: ~8-10 nodos en el path principal. Esta propuesta: ~15 nodos (incluye compose prompt auditor, Information Extractor, Split Out, Switch, 7 HTTP requests, log audit, persist). Cada nodo en N8N agrega 20-80ms de overhead (serializacion JSON entre items, ejecucion del engine). Suma facil 400-800ms extra de overhead N8N en el path completo turn-to-action.**
  - Impacto: Aunque el lead no lo nota (porque el send ocurre en nodo 7), las ACCIONES (Extractor, Handoff, Assign) se ejecutan 1-2s mas tarde que hoy. Para Request_Handoff esto importa: si el lead pide humano y el handoff tarda 2s extra en disparar, hay una ventana donde el bot podria responder DE NUEVO antes del handoff y romper UX. Necesita lock o gate en bot_config para no doble-responder.
- **Race condition entre Send WhatsApp (nodo 7) y Persist Bot Message (nodo 8) + auditor side-effects. Si el lead manda OTRO mensaje mientras el auditor de turno N todavia corre, el turno N+1 entra al workflow con el estado de lead SIN las acciones del turno N aplicadas. El conversador del turno N+1 lee atributos viejos. En conversaciones rapidas (lead que tipea seguido) esto se manifiesta como bot que 're-pregunta' datos que ya capturo en el turno anterior.**
  - Impacto: Latencia operativa del auditor (1-2s) abre ventana de inconsistencia. A escala de cientos de conversaciones simultaneas, este patron va a aparecer. Mitigacion necesaria: lock por conversation_id durante audit, o read-after-write con espera de confirmacion del auditor antes de aceptar siguiente turno. Ninguna de las dos es trivial en N8N.
- **El auditor agrega latencia inherente que SI bloquea cosas criticas: Request_Handoff. Si un lead dice 'quiero hablar con humano YA', el handoff debe disparar en <2s para que la alerta a Telegram llegue antes de que el lead se frustre. Con auditor de 1-2s + HTTP request a bot-actions (200-500ms) + alerta Telegram (300-800ms) = 1.5-3.3s desde que el lead pidio humano hasta que el agente real ve la alerta. Status quo (agente directo invoca tool) es ~500-1500ms.**
  - Impacto: Para tools no-criticas (Tag, Note) la latencia extra es invisible. Para Request_Handoff y Assign es donde mas importa y donde mas se degrada. Considerar fast-path determinista para Request_Handoff (regex sobre el mensaje del lead ANTES del conversador) que la propuesta menciona como mitigacion pero no resuelve.
- **Sin paralelizacion explicita entre Send WhatsApp (nodo 7) y Persist Bot Message (nodo 8), N8N los ejecuta secuencialmente. Persist no necesita bloquear Send. Lo mismo entre auditor y persist. La propuesta no menciona si esto se hace en paralelo via Merge node o ramas, y N8N por default es secuencial dentro de una rama.**
  - Impacto: Si no se paraleliza intencionalmente, se pierde ~200-500ms recuperables. Es fixeable pero requiere diseño explicito del workflow (ramas en paralelo + Merge). Si el founder construye esto sin ese detalle, queda 1s mas lento de lo necesario.

**Recomendacion del juez:** La latencia PERCIBIDA por el lead NO es bloqueante — la decision de mandar Send WhatsApp ANTES del auditor es correcta y mantiene el sistema en 3-6s (igual que hoy). Pero hay tres cosas que arreglar antes de produccion: (1) Implementar lock/queue por conversation_id para evitar race conditions entre turnos consecutivos cuando el auditor del turno anterior aun no termino — sin esto, a escala vas a tener bot re-preguntando datos. (2) Fast-path determinista para Request_Handoff via regex/keywords ANTES del conversador (no esperar al auditor) — bajaria latencia de handoff de 2-3s a <500ms, critico para UX. (3) Paralelizar explicitamente Send WhatsApp + Persist + auditor via ramas N8N con Merge, no dejarlo secuencial por default. Si arreglas estas 3 cosas, la latencia es aceptable para produccion. No es blocker pero requiere ingenieria deliberada del DAG, no solo conectar nodos.

### Lens: maintenance [HIGH]

**Findings:**

- **Doble fuente de verdad para 'cuando llamar una tool' — el conversador (GPT-4) decide implícitamente qué prometer al lead, y el auditor (gpt-4o-mini) decide explícitamente qué tool ejecutar. Mantener estos dos prompts sincronizados es un trabajo continuo: si agregás una auto-action nueva, tenés que tocar (a) el bloque ## AUTO-ACCIONES en agency.bot_config para el conversador, (b) el prompt del auditor con few-shots, (c) el JSON schema del Information Extractor, (d) el Switch + nueva rama HTTP. Son 4 lugares por feature.**
  - Impacto: Agregar una tool nueva pasa de 'tocar bot-actions + un bloque del prompt' (status quo) a 'tocar 4-5 archivos/nodos + recalibrar few-shots del auditor con casos reales'. Es un downgrade severo en developer velocity para el cambio más frecuente del sistema.
- **Debugging cross-LLM se vuelve cualitativamente más caro. Hoy cuando una tool no se ejecuta, el founder mira UN trace del agente y ve 'el LLM no llamó Qualify_Tool'. Con la arquitectura D, hay que correlacionar dos calls (conversador + auditor), dos prompts, dos memories de contexto distintas, y la tabla bot_audit_log nueva. Sumá que el conversador NO sabe que existen tools — así que cuando promete algo que no se ejecuta, el bug está en el gap entre dos modelos que no comparten estado.**
  - Impacto: Tiempo medio de diagnóstico de bugs de 'tool no ejecutada' se multiplica 2-3x. En producción con muchos clientes, esto es exactamente el bug más común y el que más rompe confianza (lead pide humano, bot dice ok, handoff nunca se dispara).
- **El 'fallback rule-based' propuesto en risks (regex para Request_Handoff, regla 'si bot prometió X ejecutalo') es código de glue que crece sin techo. Cada falso negativo del auditor pequeño genera presión para agregar otro fallback determinístico, hasta que terminás con un sistema híbrido donde nadie sabe si una acción se ejecutó por decisión del auditor, por regex, o por parseo de la respuesta del conversador.**
  - Impacto: En 3 meses el founder vuelve y no puede contestar 'por qué se ejecutó Assign_Tool en este turno' sin leer 3 capas: prompt del auditor + regex de fallback + parser de 'el bot prometió X'. La arquitectura erosiona hacia un Frankenstein.
- **Información Extractor con schema JSON estricto + 7 tools posibles + params variables por tool es un schema grande y frágil. Cualquier cambio de params en bot-actions (ej. Tag_Tool ahora acepta tag_color) obliga a actualizar el schema del Extractor, el prompt del auditor, los few-shots, y la rama del Switch. El nodo Information Extractor en N8N tiene un solo campo de schema — no hay versionado, no hay tests unitarios del schema.**
  - Impacto: Refactors a tools existentes — algo que hoy se resuelve cambiando una descripción de tool y el handler en bot-actions — se vuelven cross-cutting. Friccion alta para iterar tools, que es justo lo que el founder va a hacer las primeras semanas en producción.
- **El workflow N8N pasa de ~10 nodos lineales a ~15+ nodos con un Split Out + Switch de 7 ramas + 7 HTTP Requests paralelos + log nodes + alert paralela. Visualmente el grafo se vuelve un árbol denso. En N8N self-hosted en Easypanel, navegar un workflow así en 3 meses cuando volvés a debuggear es notoriamente más pesado que el actual (el founder ya tiene capturada la skill n8n-workflow-build-script — sabe el costo).**
  - Impacto: Cognitive load para entender el flujo de un turno crece de 'leer 10 nodos en línea' a 'leer 15 nodos + entender que el Switch tiene 7 ramas + entender qué pasa si el auditor devuelve array vacío vs falla'. Founder en 3 meses paga ese costo cada vez que abre el workflow.
- **Doble superficie de prompt engineering. Hoy hay UN prompt dinámico (el de Sofia) compuesto desde agency.settings + bot_config. Con la arquitectura D hay DOS prompts dinámicos: el conversador (sin tools) y el auditor (con tools, few-shots, reglas de decisión). Ambos se componen runtime desde la misma fuente de config pero con bloques distintos. El Code node que compone el prompt del auditor tiene que mantener consistencia con el del conversador para que no se contradigan.**
  - Impacto: El bug de 'auto_actions.qualify=false en agency X pero el auditor lo llama igual' aparece cuando un developer toca el bloque ## AUTO-ACCIONES PERMITIDAS solo en el conversador y olvida el auditor, o viceversa. Es un bug silencioso multi-tenant — el más caro de detectar.
- **Tabla bot_audit_log es deuda operacional nueva: crece 1 row por turno (cientos a miles de conversaciones simultáneas = decenas de miles de rows/día). Sin retention policy + indexing pensado desde día 1, en 6 meses el founder está pagando Supabase compute por una tabla de auditoría que nadie consulta excepto cuando hay bug. Pero si no la tiene, no podés debuggear el auditor.**
  - Impacto: Deuda silenciosa de costo + ops. Tener que diseñar/mantener retention + queries de análisis del auditor no estaba en el plan original — es trabajo recurrente que aparece después de pasar a producción.
- **El conversador no sabe que existen tools — esto se vende como simplificación pero rompe una propiedad útil: hoy el agente puede decir 'dame un segundo, te asigno con Juan' y simultáneamente llamar Assign_Tool, manteniendo coherencia narrativa. Con D, el conversador puede prometer sin que el auditor lo ejecute (riesgo propio del documento), o ejecutar sin que el conversador lo mencione (el lead ve 'ok, contame qué buscás' pero detrás cambió de stage). Mantener coherencia requiere reglas custom en el auditor.**
  - Impacto: Bugs de UX desincronizada se vuelven una clase nueva de issue que hoy no existe. Cada uno requiere ajustar el prompt del auditor — trabajo de prompt engineering reactivo, no escalable.

**Recomendacion del juez:** No bloquear producción por esta lens, pero tomar medidas duras antes de mergear: (1) ANTES de implementar D, escribir un ADR de 1 página que enumere exactamente qué archivos/nodos cambian cuando se agrega una tool nueva — si son más de 3, reconsiderar arquitectura C (híbrido determinista) que tiene menos superficies de cambio. (2) Si se va con D, encapsular la 'configuración de tools' en UNA fuente de verdad (ej. JSON en agency.bot_config con { tool, when_to_call, params_schema, few_shot }) que alimente RUNTIME tanto el schema del Information Extractor como el prompt del auditor — prohibir hardcodear nada del auditor en el workflow N8N. (3) Capturar skill 'agregar-tool-nueva-arquitectura-D' apenas se haga la primera, para que la segunda no requiera reverse-engineering. (4) Setup bot_audit_log con TTL de 30 días + dashboard simple (vista SQL de 'auditor decision vs conversador promise mismatch') ANTES de mergear, no después. (5) Definir explícitamente un umbral: si en la primera semana de producción aparecen ≥3 bugs distintos de desincronización conversador-auditor, rollback a status quo mejorado (opción A) y reconsiderar C. La arquitectura D es defendible si el equipo es disciplinado con prompt engineering como código versionado; es un campo minado si se trata como 'tocá el prompt y deployea'.

# Apendice C — Metodologia

## Como se ejecuto

- **Workflow tool de Claude Code** (multi-agent orchestration).
- **Pipeline pattern:** cada propuesta entra inmediatamente a evaluacion sin esperar a las demas (sin barrier sincronico entre fases para la mayor parte).
- **Phase 1 (Propuestas):** 4 agentes en paralelo, schema JSON forzado para output procesable.
- **Phase 2 (Evaluacion):** 4 jueces por propuesta (16 total), schema JSON con severity + blocker bool. Default adversarial.
- **Phase 3 (Sintesis):** 1 agente lee 4+16 outputs, produce markdown narrativo para founder.

## Por que esta metodologia

- **Diversidad de propuestas:** cada arquitecto trabaja en aislado, no se contamina con las otras propuestas. Evita groupthink.
- **Adversarial por defecto:** los jueces tenian instruccion explicita de "encontrar fallas". No son revisores amables. Esto eleva la barra para que la propuesta ganadora sobreviva escrutinio real.
- **Multi-lens:** cada arquitectura juzgada por 4 perspectivas distintas (reliability, cost, latency, maintenance). Una propuesta puede ganar en una lens y perder en otra; el sintetizador balancea.
- **Sintesis al final:** un solo agente lee TODO y prioriza segun el contexto del proyecto (multi-tenant, robustez > velocidad, founder solo).

## Cuando volver a aplicar esta tecnica

- Decisiones arquitectonicas que afectan la espina dorsal del sistema (no para microoptimizaciones).
- Cuando el founder duda entre 2+ caminos no equivalentes.
- Cuando un cambio de arquitectura tiene costo de migracion alto y no se puede volver atras facilmente.
- NO usar para tareas de implementacion concretas (es overkill).

## Costo de la mesa

- ~1.09M tokens consumidos.
- 5.3 min wall-clock.
- 21 agentes spawneados.
- Justificable porque la decision afecta semanas de desarrollo y costo operativo futuro.
